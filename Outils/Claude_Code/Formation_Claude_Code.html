Module 1

Comprendre l'outil

Avant les commandes : ce qu'un assistant en terminal fait, et ce qu'il ne fera jamais.

Définition

Claude Code en une phrase

Un assistant qui vit dans votre terminal, lit votre dépôt, écrit dans vos fichiers et exécute vos commandes — avec votre accord, à chaque étape.

Il lit

Vos fichiers, votre historique git, la sortie de vos commandes, les pages web que vous lui donnez.

Il écrit

Dans vos fichiers, directement. Pas de copier-coller depuis un chat.

Il exécute

Vos tests, vos scripts, git. Et il lit ce que ça renvoie, pour corriger tout seul.

La différence avec un chat n'est pas la qualité du modèle : c'est la boucle. Écrire, lancer, lire l'erreur, corriger. Sans vous.
💬 Combien de fois par jour copiez-vous du code d'un chat vers votre éditeur ?
Positionnement

Terminal ou éditeur : ce que ça change vraiment

Dans l'éditeur (Copilot)Dans le terminal (Claude Code)
Unité de travailLa ligne, la fonction, le fichier ouvertLa tâche : plusieurs fichiers, plusieurs commandes
Ce qu'il voitCe qui est ouvert, plus ce que vous mentionnezTout le dépôt, qu'il explore lui-même
VérificationVous lancez les testsIl lance les tests et lit le résultat
RythmeSeconde par seconde, en tapantMinute par minute, par tâche

Les deux ne s'opposent pas : la plupart des développeurs qui les utilisent sérieusement gardent Copilot pour écrire, et l'assistant en terminal pour les tâches qui touchent plusieurs fichiers.

Premiers pas

Les cinq premières minutes, dans l'ordre

  • /init — il lit le projet et rédige un premier CLAUDE.md. Relisez-le et corrigez-le : ce qu'il devine est correct, ce qu'il ne peut pas deviner manque.
  • /context — voir ce qu'il a en mémoire, et combien il en reste.
  • Une première question de lecture, pas d'écriture : « explique-moi l'architecture de ce projet ».
  • /plan — décrire une modification sans l'écrire. Lire. Corriger. Approuver.
  • /diff — relire ce qui a réellement changé, avant tout commit.
L'erreur numéro un du premier jour : demander tout de suite une grosse modification. On obtient trois cents lignes qu'on ne relit pas, on prend peur, et on désinstalle. Commencez par lui faire lire.

Mécanique

La boucle, en quatre temps

  • 1 · Il explore. Il cherche les fichiers pertinents avec des outils de recherche, pas en lisant tout le dépôt. Vous voyez chaque recherche défiler.
  • 2 · Il propose. Une modification de fichier, une commande à lancer. Selon le mode de permission, il vous demande ou il agit.
  • 3 · Il exécute. Vos tests, votre linter, git.
  • 4 · Il lit le résultat et recommence si ça a échoué — souvent trois ou quatre fois, sans vous solliciter.
C'est le point 4 qui fait toute la différence. Un chat vous rend un code plausible ; un agent vous rend un code qui passe les tests — à condition que vous ayez des tests.
💬 Sans tests, sur quoi la boucle se referme-t-elle ?
Limites

Ce qu'il voit, et ce qu'il ignore complètement

Il voit

  • Les fichiers du dossier où vous l'avez lancé
  • L'historique git, les diffs, les branches
  • La sortie des commandes qu'il lance
  • Ce que vous lui donnez : fichiers, images, URL
  • Les serveurs MCP que vous avez branchés

Il ignore

  • Ce qui est hors du dossier (sauf /add-dir)
  • Votre base de données, vos journaux de production
  • Ce que votre équipe a décidé en réunion
  • Pourquoi ce contournement bizarre existe depuis 2019
  • Les sessions précédentes, sauf CLAUDE.md
La colonne de droite est exactement le contenu d'un bon CLAUDE.md. C'est le sujet du module suivant.

Module 2

Le contexte : la seule chose qui compte vraiment

Un assistant bien informé sur un petit modèle bat un assistant ignorant sur un grand modèle.

CLAUDE.md

La mémoire du projet

Un fichier markdown, à la racine du dépôt, lu automatiquement au démarrage de chaque session. Versionné, donc partagé avec toute l'équipe.

  • Ce qu'on y met : l'architecture en une table, les conventions, les règles métier qui ne se devinent pas, les commandes du projet, les interdits.
  • Ce qu'on n'y met pas : ce qui se lit dans le code, un tutoriel, l'historique du projet, des politesses.
  • La bonne longueur : une page. Passé deux, il n'est plus lu attentivement — ni par l'assistant, ni par vos collègues.
  • Le test : écrivez-le comme une note à un nouveau collègue compétent qui arrive lundi.
Un CLAUDE.md qui ment est pire que pas de CLAUDE.md du tout. Relisez-le le jour où vous changez d'architecture.

Code · MiniCRM

Le CLAUDE.md de notre projet, extrait

codebase_minicrm/CLAUDE.md
## Architecture

| Fichier              | Rôle                          | Ne doit jamais            |
|----------------------|-------------------------------|---------------------------|
| js/modele.js         | Valider, normaliser, formater | toucher au DOM            |
| js/depot.js          | Ranger, retrouver, trier      | contenir une règle métier |
| js/statistiques.js   | Calculer                      | avoir d'effet de bord     |
| js/vue.js            | Produire du HTML              | calculer quoi que ce soit |

## Règles métier — à ne pas casser

1. Seul un contact au statut `client` compte dans le chiffre d'affaires.
   Un prospect peut porter un montant : c'est une ESTIMATION, pas un revenu.
2. Un `client` doit avoir un montant supérieur à zéro.
3. Deux contacts ne peuvent pas partager la même adresse e-mail.
4. Un contact `inactif` n'apparaît jamais dans la liste « à rappeler » :
   il a dit non, on n'insiste pas.

## Ce qu'il ne faut pas faire ici

- Ajouter une dépendance npm, un bundler, TypeScript ou un framework.
- Renommer les fonctions publiques : index.html et les tests s'y réfèrent.
- Utiliser innerHTML avec une valeur non échappée.
Les quatre règles métier sont le cœur du fichier. Aucune ne se devine en lisant le code : ce sont des décisions du métier. C'est exactement ce qu'un assistant ne peut pas inventer.

Alimenter

Trois façons de lui donner ce qu'il n'a pas

  • @chemin/fichier.js — mentionner un fichier dans votre message. L'autocomplétion s'ouvre dès le @.
  • !commande — lancer une commande shell et injecter sa sortie dans la conversation. !git log --oneline -20 lui donne l'histoire récente en une ligne.
  • Coller une image — Ctrl+V : une capture d'écran d'un bug, d'une maquette, d'un tableau blanc. Il la lit.
  • /add-dir ../autre-projet — ajouter un second dossier à la session, sans quitter celle-ci.
Le réflexe qui change tout : au lieu de décrire une erreur, lui donner l'erreur. !node run-tests.js vaut mieux que « les tests plantent ».
💬 Combien de fois avez-vous paraphrasé un message d'erreur au lieu de le coller ?
Fenêtre de contexte

Gérer la mémoire d'une longue session

  • /context — voir ce qui occupe la mémoire : les fichiers lus, l'historique, les outils. Le premier réflexe quand les réponses se dégradent.
  • /compact — résumer la conversation pour libérer de la place. On peut guider : /compact garde les décisions d'architecture.
  • /clear — repartir de zéro. Le CLAUDE.md reste, l'historique disparaît. À faire entre deux tâches sans rapport.
  • /rewind — revenir en arrière, dans le code et dans la conversation. Le filet de sécurité qu'on oublie d'utiliser.
Le symptôme classique d'un contexte saturé : il « oublie » une consigne donnée vingt minutes plus tôt, ou recommence une modification déjà faite. Ce n'est pas le modèle qui faiblit, c'est la mémoire qui déborde.

Module 3

Décider avant de laisser écrire

Le mode plan et les modes de permission : les deux réglages qui séparent l'outil utile de l'outil dangereux.

Mode plan

Faire décrire avant de faire écrire

/plan, ou Shift+Tab jusqu'au mode « plan ». Il explore, il réfléchit, il propose — et il n'écrit aucun fichier tant que vous n'avez pas approuvé.

  • Utilisez-le pour toute tâche de plus de dix minutes, sans exception.
  • Lisez le plan comme vous liriez celui d'un collègue : où se trompe-t-il de fichier ? Qu'a-t-il oublié ? Qu'a-t-il ajouté qu'on ne demandait pas ?
  • Corrigez le plan dans le chat, avant d'approuver. Corriger un plan coûte trois lignes ; corriger trois cents lignes de code coûte une heure.
  • Un bon plan nomme les fichiers touchés, les tests à ajouter, et ce qu'il ne va pas faire.
C'est le geste qui distingue les gens qui gardent le contrôle de leur base de code de ceux qui la subissent. Il ne coûte que deux minutes.

Permissions

Les modes, et quand utiliser chacun

ModeComportementQuand
defaultDemande avant chaque écriture et chaque commandeLe premier jour, et sur un dépôt que vous ne connaissez pas
acceptEditsÉcrit les fichiers sans demander, demande pour les commandesLe mode de travail courant, quand git vous protège
planN'écrit rien du toutExploration, conception, revue
bypassPermissionsNe demande plus rienUniquement dans un conteneur jetable ou une machine virtuelle
  • Shift+Tab fait tourner les modes, sans quitter la session.
  • /permissions ouvre les règles fines : autoriser Bash(node run-tests.js) une fois pour toutes, interdire Bash(git push:*) définitivement.
--dangerously-skip-permissions porte ce nom pour une raison. Sur votre machine de travail, avec vos clés SSH et vos accès en production, ne l'utilisez pas.

Code · MiniCRM

Les permissions, écrites une fois pour l'équipe

codebase_minicrm/.claude/settings.json
{
  "permissions": {
    // Ce que Claude peut faire sans demander à chaque fois.
    "allow": [
      "Bash(node run-tests.js)",
      "Bash(git status)",
      "Bash(git diff:*)",
      "Read", "Grep", "Glob"
    ],

    // Ce qui reste TOUJOURS interdit, même si on approuve tout le reste.
    // Une règle « deny » gagne toujours contre une règle « allow ».
    "deny": [
      "Bash(rm -rf:*)",
      "Bash(git push:*)",
      "Bash(npm install:*)",
      "Read(./.env)",
      "Read(./**/*.pem)"
    ]
  }
}
.claude/settings.json est versionné : il vaut pour toute l'équipe. Vos préférences personnelles vont dans .claude/settings.local.json, qui ne l'est pas.

Jugement

Trois questions avant d'accepter une modification

  • Est-ce que je comprends chaque ligne ? Si non, demandez une explication avant d'accepter. Du code qu'on ne comprend pas est du code qu'on ne saura pas réparer à 3 h du matin.
  • Est-ce que ça fait uniquement ce que j'ai demandé ? Le travers le plus fréquent est d'en faire trop : renommer au passage, « améliorer » une fonction voisine, ajouter une abstraction dont personne n'a besoin.
  • Est-ce que les tests couvrent la modification ? Pas « est-ce que les tests passent » — est-ce qu'ils testent ce qui vient de changer.
/diff avant chaque commit, sans exception. Trente secondes de lecture évitent des semaines de dette.

Compétences

Écrire vos propres commandes

Une compétence (skill) est un fichier markdown avec un en-tête. Elle devient une commande /nom, et l'assistant peut aussi l'invoquer tout seul quand la situation s'y prête.

  • .claude/skills/nom/SKILL.md — dans le projet, versionné, partagé avec l'équipe.
  • ~/.claude/skills/nom/SKILL.md — chez vous, sur tous vos projets.
  • L'en-tête déclare le name, la description (c'est elle qui décide quand la compétence est utile), et éventuellement allowed-tools.
  • $ARGUMENTS, $0, $1 reçoivent ce que vous tapez après la commande.
  • !`commande` exécute une commande avant l'envoi et injecte sa sortie : la compétence arrive avec les données déjà là.
C'est la fonctionnalité la plus rentable de l'outil : tout ce que vous répétez trois fois par semaine mérite une compétence.

Code · MiniCRM

La compétence /verifier, en entier

codebase_minicrm/.claude/skills/verifier/SKILL.md
---
name: verifier
description: Vérifie l'état du projet avant de proposer une modification.
allowed-tools: Bash(node run-tests.js) Bash(git status) Bash(git diff:*) Read Grep
---

## Contexte

### État de git
!`git status --short`

### Résultat des tests
```!
node run-tests.js 2>&1 | tail -5
```

## Ce qu'il faut faire

Analyse ce qui précède et réponds en quatre points, sans préambule :

1. **Tests** : combien passent, combien échouent, lequel corriger d'abord.
2. **Portée** : les fichiers modifiés relèvent-ils d'une seule intention ?
3. **Règles métier** : le diff touche-t-il l'une des cinq règles de CLAUDE.md ?
4. **Verdict** : `PRÊT À VALIDER` ou `À CORRIGER`, en une ligne.

N'écris rien d'autre. Ne modifie aucun fichier.
Les commandes entre !` ` tournent avant l'envoi : l'assistant reçoit le vrai état de git et le vrai résultat des tests, pas une demande d'aller les chercher.

Sous-agents et parallélisme

Déléguer une partie du travail à une session isolée, qui ne pollue pas votre contexte.

Sous-agents

Pourquoi déléguer plutôt que tout faire dans la même session

  • Le contexte reste propre. Une exploration qui lit quarante fichiers remplit la mémoire. Dans un sous-agent, seul le résultat revient.
  • Le rôle est différent. Un relecteur ne doit pas avoir écrit le code qu'il relit : il verrait ce qu'il a voulu faire, pas ce qu'il a fait.
  • Les outils sont restreints. Un sous-agent d'exploration en lecture seule ne peut rien casser, même en cas de mauvaise interprétation.
  • Ça tourne en parallèle. Plusieurs sous-agents avancent pendant que vous continuez à travailler.

@nom-de-lagentL'appeler dans un message

Code · MiniCRM

Le sous-agent relecteur

codebase_minicrm/.claude/agents/relecteur.md
---
name: relecteur
description: Relit une modification avec l'oeil d'un développeur senior.
tools: Read, Grep, Glob, Bash
model: sonnet
---

Tu es un développeur senior qui relit le code d'un collègue sur MiniCRM.
Les règles du projet sont dans CLAUDE.md. Lis-le en premier.

## Ce que tu cherches, dans cet ordre

1. Une RÈGLE MÉTIER cassée. C'est le seul défaut qui coûte vraiment cher :
   il ne fait pas planter le programme, il donne un chiffre faux.
2. Une valeur non échappée qui entre dans du HTML.
3. Une fonction placée dans la mauvaise couche.
4. Un cas limite non testé : liste vide, null, division par zéro,
   date invalide, chaîne avec accent ou apostrophe.
5. Un commentaire qui répète le code au lieu d'expliquer le pourquoi.

## Comment tu réponds

Une liste, du plus grave au moins grave. Pour chaque point : le fichier
et la ligne, le problème en une phrase, la correction en une phrase.

Si tu ne trouves rien de sérieux, dis-le en une ligne. Ne remplis pas.
Ne modifie aucun fichier : tu relis, tu ne corriges pas.
Deux détails qui comptent : tools ne contient ni Edit ni Write — il ne peut pas corriger. Et « ne remplis pas » évite la liste de dix remarques cosmétiques qui noie la vraie.

Hooks, MCP, Git : faire entrer l'assistant dans votre chaîne de travail.

Hooks

Déclencher une commande sur un événement

Un hook est une commande shell lancée automatiquement à un moment précis de la session. Ce n'est pas l'assistant qui décide : c'est votre configuration.

ÉvénementLe cas d'usage typique
PostToolUseRelancer les tests ou le formateur après chaque écriture
PreToolUseRefuser une commande dangereuse avant qu'elle ne parte
SessionStartAfficher l'état du dépôt, rappeler la branche courante
StopJournaliser ce qui a été fait, prévenir l'équipe
UserPromptSubmitInjecter du contexte à chaque message
/hooks affiche les hooks actifs. Ils se configurent dans .claude/settings.json, donc ils sont versionnés et partagés.
💬 Quel geste répétez-vous manuellement après chaque modification de fichier ?
Code · MiniCRM

Le hook qui relance les tests, tout seul

codebase_minicrm/.claude/settings.json
{
  "hooks": {
    "PostToolUse": [
      {
        // Ce hook se déclenche après chaque Edit ou Write.
        "matcher": "Edit|Write",
        "hooks": [
          {
            "type": "command",
            "command": "node run-tests.js > /dev/null 2>&1 && echo 'Tests au vert.' || echo 'ATTENTION : des tests sont en échec.'"
          }
        ]
      }
    ]
  }
}
Effet concret : l'assistant modifie un fichier, voit immédiatement « ATTENTION », et corrige avant de vous rendre la main. Sans le hook, il vous rendrait un code cassé et vous le découvririez plus tard.

MCP

Brancher vos systèmes

Le protocole vu au jour 3. Côté Claude Code, il tient en trois commandes.

terminal
# Ajouter un serveur, pour vous seulement
claude mcp add rag-local -- python chemin/vers/serveur_mcp.py

# Voir l'état des serveurs, dans une session
/mcp

# Déboguer quand ça ne se connecte pas
claude --debug=mcp
  • Pour partager un serveur avec l'équipe : un fichier .mcp.json à la racine du dépôt, versionné.
  • Ce que ça change : l'assistant interroge votre base documentaire, votre suivi de tickets, votre supervision — sans que vous copiiez-colliez quoi que ce soit.
  • Ce que ça ne change pas : la prudence. Un outil MCP en écriture est un outil qui peut agir sur vos systèmes.
Le fichier .mcp.json de MiniCRM pointe déjà vers le serveur RAG que vous avez construit au jour 3.

🔧 Travaux pratiques

Prendre en main MiniCRM

45 minutes · seul · dossier <code class="inline">codebase_minicrm/</code>
  1. Ouvrez un terminal dans le dossier et lancez claude.
  2. /status puis /context : que voit-il déjà, sans que vous ayez rien demandé ?
  3. Demandez : « explique-moi l'architecture de ce projet en cinq lignes ». Comparez sa réponse au CLAUDE.md.
  4. Renommez temporairement CLAUDE.md en CLAUDE.off, faites /clear, reposez la même question. Notez la différence.
  5. Remettez le fichier en place.
  6. /plan puis : « ajoute une flèche de tri sur la colonne active du tableau » (sujet A1). Lisez le plan, corrigez-le, approuvez.
  7. /diff, puis /verifier.
Livrable : le plan corrigé (copié dans votre fiche), la fonctionnalité qui marche, les 90 tests au vert, et deux phrases sur ce que le CLAUDE.md a changé.
🔧 Travaux pratiques

Attaquer la dette technique, proprement

1 h 15 · en binôme · <code class="inline">DETTE_TECHNIQUE.md</code>
  1. Lisez DETTE_TECHNIQUE.md et choisissez deux sujets. Deux, pas six.
  2. Pour chacun : /plan, lecture, correction, approbation.
  3. Après chaque sujet : /diff, puis @relecteur relis ce diff.
  4. Comparez ce que dit le relecteur à ce que vous aviez vu vous-même. Qui a trouvé quoi ?
  5. Faites un commit par sujet. Laissez-le rédiger le message, puis relisez-le.
  6. Créez votre propre compétence : .claude/skills/commit-propre/SKILL.md, qui lance les tests, montre le diff et propose un message de commit.
  7. Testez-la : /commit-propre.
Livrable : deux sujets traités, deux commits propres, une compétence maison qui fonctionne, et la liste de ce que le relecteur a vu et que vous aviez manqué.

Automatiser et brancher

1 heure · en binôme
  1. Ouvrez .claude/settings.json et lisez le hook PostToolUse déjà en place.
  2. Désactivez-le, demandez une modification qui casse un test, observez. Réactivez-le, refaites la même demande. Notez la différence de comportement.
  3. Ajoutez un hook SessionStart qui affiche la branche git courante et le nombre de fichiers modifiés.
  4. Branchez le serveur MCP du jour 3 : claude mcp add rag-local -- python ..., puis /mcp.
  5. Posez une question dont la réponse est uniquement dans la base documentaire. Vérifiez qu'il cite le fichier source.
  6. Créez un sous-agent testeur qui écrit des tests et n'a pas le droit de modifier js/.

Sur le contexte

  • Lancer claude hors du projet
  • Ne jamais écrire de CLAUDE.md

  • Décrire une erreur au lieu de la coller

Sur le contrôle

  • Sauter le mode plan « pour aller plus vite »
  • Accepter un diff sans le lire
  • Travailler sans tests, puis s'étonner
  • Demander cinq choses dans un seul message
  • Passer en bypassPermissions par confort
Neuf de ces dix erreurs ont la même cause : vouloir gagner deux minutes. Elles en coûtent chacune une heure.

Limites

Ce qu'il ne faut pas lui confier

  • Une décision d'architecture qui engage deux ans. Il argumente très bien en faveur de ce que vous venez de suggérer. Ce n'est pas un contradicteur.
  • Du code que personne de votre équipe ne saura relire. Si le seul relecteur possible est l'assistant lui-même, vous avez créé une dépendance, pas un gain.
  • Ce qui touche à de l'argent, à de la santé ou à du droit, sans relecture humaine ligne à ligne.
  • Vos secrets. Un .env lu est un .env parti. Mettez-le en « deny ».
  • La production. Aucun agent ne devrait avoir un accès en écriture à votre production. Aucun.
La bonne question n'est jamais « est-ce qu'il en est capable ? », mais « qui répond si c'est faux ? ». La réponse est toujours vous.
