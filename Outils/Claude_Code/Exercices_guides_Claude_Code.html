Claude Code · Exercices guidés

Trois exercices sur MiniCRM, treize étapes. Le projet est sain : 90 tests au vert, de la dette technique, et des fonctionnalités manquantes.

Durée totale 3 h 10 Niveau débutant à intermédiaire Code base MiniCRM · variante dette technique Tests 90 au vert
Chaque étape tient en une action. Faites-les dans l'ordre. Les cases se cochent à l'écran et la page retient vos coches ; les zones de texte sont à remplir — c'est là que se joue l'apprentissage. Le bouton Exporter en PDF vous en donne une copie à garder.
Le projet est sain : les 90 tests passent. Rien n'est cassé. Ce qui vous attend, c'est de la dette technique et des fonctionnalités manquantes — la situation où un assistant agentique est le plus utile, et la plus proche de votre quotidien.

2.3Écrire votre première compétence
Intermediaire

Créez .claude/skills/commit-propre/SKILL.md. Elle doit lancer les tests, montrer le diff, et proposer un message de commit.

---
name: commit-propre
description: Vérifie et prépare un commit propre sur MiniCRM.
allowed-tools: Bash(node run-tests.js) Bash(git diff:*) Bash(git status) Read
---

## Contexte

### Modifications
!`git diff --stat`

### Tests
```!
node run-tests.js 2>&1 | tail -3
```

## Ce qu'il faut faire

1. Si des tests échouent, dis-le et ARRÊTE-TOI.
2. Sinon, vérifie que le diff relève d'une SEULE intention.
3. Propose un message de commit d'une ligne, en français, à l'impératif.

N'écris rien d'autre. Ne fais pas le commit toi-même.
  1. Enregistrez le fichier.
  2. Dans la session, tapez /commit-propre.
  3. Si la commande n'apparaît pas : vérifiez le chemin et l'en-tête YAML.

Exercice 3 · Automatiser et brancher

Durée : 1 heure · En binôme

3.1L'expérience du hook
Intermediaire
  1. Ouvrez .claude/settings.json et lisez le hook PostToolUse.
  2. Commentez-le temporairement (renommez la clé hooks en hooks_off).
  3. Redémarrez la session, demandez une modification qui casse un test (par exemple : « change le seuil de 90 jours à 90 heures dans contactsDormants »).
  4. Observez : vous rend-il la main avec un test cassé ?
  5. Réactivez le hook, redémarrez, refaites la même demande.

La différence de comportement, en deux phrases

Ce que vous venez d'observer : le hook ne rend pas les tests plus utiles, il rend l'assistant plus autonome. Il voit son erreur avant vous.
3.2Ajouter un hook de démarrage
Intermediaire

Dans .claude/settings.json, ajoutez un hook SessionStart qui affiche la branche git et le nombre de fichiers modifiés.

"SessionStart": [
  {
    "hooks": [
      {
        "type": "command",
        "command": "echo \"Branche : $(git branch --show-current) — $(git status --short | wc -l) fichier(s) modifié(s)\""
      }
    ]
  }
]

3.4Un sous-agent aux outils restreints
Avance

Créez .claude/agents/testeur.md : un agent qui écrit des tests et n'a pas le droit de modifier js/.

---
name: testeur
description: Écrit des tests pour MiniCRM. Ne modifie jamais le code de production.
tools: Read, Grep, Glob, Edit, Bash
model: sonnet
---

Tu écris des tests pour MiniCRM, dans le dossier tests/ UNIQUEMENT.

Tu ne modifies JAMAIS un fichier de js/. Si le code te semble faux,
tu écris le test qui le prouve, et tu le signales. Tu ne le corriges pas.

Chaque test que tu écris contient au minimum :
- le cas nominal ;
- un cas limite : liste vide, null, division par zéro, date invalide ;
- un cas d'erreur : ce qui doit être refusé, et pourquoi.

Le nom du test se lit comme une phrase de spécification, en français.
  1. Appelez-le : @testeur écris les tests manquants pour exporterCsv().
  2. Lisez les tests produits. Sont-ils utiles ?
  3. Cassez volontairement exporterCsv() et relancez : les nouveaux tests deviennent-ils rouges ?

Le test le plus utile qu'il a écrit

Un test qui ne sert à rien, s'il y en a un
