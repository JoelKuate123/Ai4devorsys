Module 1

Comprendre l'agent

Ce qui distingue Codex d'un chat, et pourquoi le bac à sable est sa caractéristique principale.

Définition

Codex en une phrase

Un agent de code qui lit votre dépôt, modifie vos fichiers et exécute vos commandes à l'intérieur d'un bac à sable, avec un niveau d'autorisation que vous choisissez.

Trois surfaces

Le terminal (codex), l'extension d'éditeur, et le cloud pour les tâches longues. La même configuration partout.

Un bac à sable

Par défaut, il n'écrit que dans le dossier de travail et n'a pas accès au réseau. Ce n'est pas une option : c'est le comportement normal.

Un fichier ouvert

AGENTS.md est une convention partagée par plusieurs agents, pas un format propriétaire.

La question à se poser n'est jamais « qu'est-ce qu'il sait faire ? » mais « qu'est-ce qu'il a le droit de faire, là, maintenant ? ». C'est tout l'objet du module 2.

Boucle

Pourquoi les tests au rouge sont le terrain idéal

  • Le succès est vérifiable. « Le test passe » n'est pas une opinion. L'agent sait quand il a fini, et vous aussi.
  • La boucle est courte. Lancer, lire l'échec, corriger, relancer : quelques secondes par tour, sans vous solliciter.
  • L'erreur est bornée. Dans un bac à sable, une mauvaise idée abîme un fichier du projet, pas votre système.
  • La régression se voit. Si une correction casse autre chose, les 89 autres tests le disent immédiatement.
Le corollaire est brutal : sans tests, un agent n'a aucun moyen de savoir s'il a raison. Il produira du code plausible et s'arrêtera quand il estimera avoir fini. C'est vous qui découvrirez le problème, plus tard.

Approbations

Quand il s'arrête pour vous demander

PolitiqueComportementQuand
on-requestIl demande quand il estime en avoir besoinLe réglage par défaut de ce projet. Le bon équilibre.
on-failureIl demande seulement après un échecUne tâche longue et bien cadrée, sur une branche
neverIl ne demande jamaisIntégration continue, conteneur jetable. Pas votre poste.
  • /permissions change le réglage sans quitter la session.
  • --full-auto est un raccourci pratique : workspace-write plus des approbations allégées.
  • --dangerously-bypass-approvals-and-sandbox (alias --yolo) désactive les deux. Le nom est explicite : c'est une option de conteneur, pas de poste de travail.
Le vrai risque n'est pas que l'agent soit malveillant. C'est qu'il exécute avec zèle une instruction mal comprise — et qu'il n'y ait aucun garde-fou entre cette instruction et votre disque.

Méthode

Lire un échec de test correctement

C'est le geste central de la journée, et celui qu'on fait le plus mal. Un échec de test contient trois informations distinctes — on n'en lit souvent qu'une.

  • 1 · Ce que le test attendait. C'est la spécification. Relisez-la avant de regarder le code : elle dit ce que le métier veut, pas ce que le code fait.
  • 2 · Ce que le code a produit. L'écart entre les deux est le symptôme, pas la cause.
  • 3 · Le nom du test. « trie les nombres, pas leur écriture » vous dit déjà tout : le tri fonctionne, mais pas sur le bon type.
sortie de node run-tests.js
  ECHEC trie les nombres, pas leur écriture
         attendu 0, obtenu 0

# Piège : « attendu 0, obtenu 0 » n'est PAS une erreur d'affichage.
# Le test compare le premier élément après tri. Les deux valent zéro,
# mais l'ordre du reste est faux. Le message ne dit pas tout :
# c'est le NOM du test qui contient l'information utile.
Demandez toujours la cause avant la correction. Un agent à qui l'on dit « corrige » corrige le symptôme ; un agent à qui l'on dit « explique-moi pourquoi » trouve la cause — et la correction devient évidente.

Module 3

AGENTS.md, le contexte partagé

Le fichier qui évite de tout réexpliquer — et qui sert à plusieurs agents, pas à un seul.

AGENTS.md

Un format ouvert, plusieurs outils

AGENTS.md, à la racine du dépôt, est lu automatiquement par Codex — et par plusieurs autres agents de code. C'est une convention, pas un format propriétaire.

  • Ce qu'on y met : ce que fait le projet, comment lancer les tests, l'architecture, les conventions, les règles métier, les interdits.
  • Ce qui compte le plus : les commandes. Un agent qui ne sait pas comment lancer vos tests travaille à l'aveugle.
  • Ce qu'on n'y met pas : ce qui se lit dans le code, l'historique du projet, un tutoriel du langage.
  • /init en génère un premier jet à partir du dépôt. Relisez-le : ce qu'il devine est juste, ce qu'il ne peut pas deviner manque.
Le test de qualité est le même que pour un README : donnez-le à quelqu'un qui arrive lundi. S'il peut lancer les tests et éviter les trois pièges du projet, le fichier est bon.

## L'état actuel : les tests sont au rouge

```bash
node run-tests.js
```

## Les règles métier

1. Seul un contact au statut `client` compte dans le chiffre d'affaires.
   Un prospect peut porter un montant : c'est une estimation, pas un revenu.
2. Un `client` doit avoir un montant supérieur à zéro.
3. Deux contacts ne peuvent pas partager la même adresse e-mail.
   Un contact qu'on modifie garde évidemment droit à sa propre adresse.
4. Un contact `inactif` n'apparaît jamais dans la liste « à rappeler ».

## Interdits

- Ajouter une dépendance, TypeScript, un bundler ou un framework.
- MODIFIER UN TEST POUR LE FAIRE PASSER. Si un test te semble faux,
  dis-le, ne le corrige pas.
- Corriger plusieurs défauts dans le même commit.
L'interdit en majuscules est le plus important du fichier. Sans lui, un agent pressé « répare » la suite de tests au lieu du code — et vous perdez le seul garde-fou dont vous disposiez.

Trois garde-fous

Plan, diff, review : dans cet ordre

/plan — avant

Il décrit ce qu'il compte faire, sans écrire une ligne. Vous lisez, vous corrigez, vous approuvez. Corriger un plan coûte trois lignes.

/diff — pendant

Ce qui a réellement changé, pas ce qu'il dit avoir changé. Les deux diffèrent plus souvent qu'on ne le croit.

/review — après

Une relecture automatique du travail en cours. Elle ne remplace pas la vôtre : elle attrape ce que vous auriez sauté en fin de journée.

Les trois ensemble prennent moins de deux minutes. C'est le prix du contrôle, et il est dérisoire comparé au coût d'un défaut découvert trois semaines plus tard.
Le raccourci le plus tentant : sauter /plan parce que « c'est une petite modification ». C'est justement sur les petites modifications que l'agent en fait trop.

Code · MiniCRM

Écrire sa propre commande

codebase_minicrm/.codex/prompts/corriger-un-bogue.md
Corrige UN SEUL défaut de MiniCRM, celui qui concerne : $1

Méthode imposée, sans sauter d'étape :

1. Lance `node run-tests.js` et identifie le test en échec correspondant.
2. Lis le test : il dit exactement ce qui est attendu. Ne le modifie pas.
3. Explique la CAUSE en deux phrases, avant de toucher au code.
   La cause est rarement à l'endroit du symptôme.
4. Fais la correction la PLUS PETITE possible. Ne refactorise rien au passage.
5. Relance les tests : ce test passe, et aucun autre ne casse.
6. Propose un message de commit d'une ligne, en français, à l'impératif.

Si le test te semble faux, dis-le et arrête-toi. Ne corrige jamais un test
pour le faire passer.
Un fichier markdown dans .codex/prompts/ devient une commande /corriger-un-bogue. $1 reçoit ce que vous tapez après. Versionné, donc partagé avec l'équipe.

Réglages fins

Modèle et effort de raisonnement

  • /model change de modèle sans quitter la session.
  • model_reasoning_effort règle la profondeur de raisonnement : low, medium, high.
  • Sur une correction de bogue, l'effort élevé paie vraiment. La cause est rarement à l'endroit du symptôme, et c'est exactement ce que le raisonnement sert à trouver.
  • Sur une tâche mécanique — renommer, formater, extraire une constante — l'effort élevé ne change rien et coûte du temps.
  • /fast bascule vers un service plus rapide quand la latence compte plus que la profondeur.
Le réflexe utile : commencer bas, monter quand ça bloque. L'inverse — tout en high par défaut — coûte cher sans rien améliorer sur 80 % des demandes.

Automatiser

codex exec : le mode sans interface

terminal
# Une tâche, une commande, aucune interaction.
codex exec "liste les fonctions de js/ qui n'ont aucun test"

# En intégration continue : lecture seule, jamais d'approbation,
# et une sortie exploitable par un script.
codex exec \
  --sandbox read-only \
  --ask-for-approval never \
  --json \
  "Relis le diff de cette branche et signale uniquement les vrais problèmes"

# Reprendre une session précédente, sans repartir de zéro
codex resume

# Appliquer localement le diff produit par une tâche cloud
codex apply
--ask-for-approval never ne s'utilise qu'associé à --sandbox read-only, ou dans un conteneur jetable. Les deux options se lisent ensemble, jamais séparément.

Déléguer

Le cloud, et ce qu'il change

  • Une tâche longue tourne ailleurs. Vous récupérez un diff, que vous appliquez avec codex apply — ou que vous jetez.
  • Plusieurs tâches en parallèle. Trois corrections indépendantes avancent pendant que vous travaillez sur autre chose.
  • L'environnement est reproductible. Ce n'est plus « ça marche sur ma machine ».
  • Ce qui ne change pas : il faut lire le diff. Un diff arrivé du cloud n'est pas plus fiable qu'un diff écrit sous vos yeux — il est simplement plus facile à accepter sans regarder.
Le risque de la délégation n'est pas technique, il est humain : plus le travail est distant, moins on le relit. C'est exactement l'inverse de ce qu'il faudrait faire.
Règle simple : une tâche déléguée doit être vérifiable automatiquement. « Fais passer les tests » se délègue. « Améliore l'architecture » ne se délègue pas.

Revue

Ce qu'une relecture automatique attrape, et ce qu'elle rate

Ce qu'elle attrape bien

  • Un cas limite non traité : liste vide, null, division par zéro
  • Une valeur non échappée dans du HTML
  • Une erreur avalée silencieusement
  • Une incohérence entre le code et son commentaire
  • Un test modifié au passage

Ce qu'elle rate

  • Une règle métier qu'elle ne connaît pas
  • Un choix d'architecture discutable mais correct
  • Ce qui manque : la fonctionnalité oubliée
  • Le fait que la demande initiale était mauvaise
  • Ce que votre équipe a décidé la semaine dernière
La colonne de gauche est mécanique, donc automatisable. La colonne de droite demande de connaître le contexte — et c'est précisément ce qu'un AGENTS.md bien écrit lui donne, en partie.
Une revue automatique qui ne trouve rien n'est pas une bonne nouvelle : c'est une information sur la revue, pas sur le code.

Coût

Ce que consomme un agent, et comment le tenir

  • Un agent consomme bien plus qu'un chat : il lit des fichiers, lance des commandes, lit les sorties, recommence. Une correction de bogue peut représenter quinze allers-retours.
  • /status affiche la consommation de la session en cours. Regardez-la en fin de journée, la première semaine.
  • Le premier levier est le même qu'au jour 2 : le choix du modèle et de l'effort de raisonnement.
  • Le deuxième est le contexte : une session ouverte depuis six heures renvoie l'historique entier à chaque tour. /compact ou /new entre deux sujets.
  • Le troisième est la formulation : une tâche vague fait explorer longtemps. Un /plan bien cadré coûte moins qu'une divagation.
L'économie la plus efficace n'est pas technique : c'est de découper. Six petites tâches vérifiables coûtent moins et donnent un meilleur résultat qu'une grosse tâche floue.

🔧 Travaux pratiques

Les trois premiers défauts

1 heure · seul · <code class="inline">BOGUES.md</code>
  1. node run-tests.js : 9 échecs sur 90. Lisez-les tous avant de toucher à quoi que ce soit.
  2. codex puis /status : notez le modèle, le mode d'approbation et le bac à sable.
  3. Lisez BOGUES.md : six symptômes, aucun emplacement.
  4. Défaut 1 (les centimes perdus) : /plan d'abord. Faites-lui expliquer la cause avant de corriger.
  5. Corrigez, /diff, relancez les tests, commit.
  6. Défauts 2 et 3, avec la commande du projet : /corriger-un-bogue le client à zéro euro.
  7. Après chaque correction : les tests concernés passent, et aucun autre ne casse.
Livrable : trois défauts corrigés, trois commits séparés, et pour chacun une phrase écrite expliquant la cause — pas le symptôme.
🔧 Travaux pratiques

Les trois derniers, et la revue

1 h 10 · en binôme
  1. Corrigez les défauts 4, 5 et 6. Un par un, jamais ensemble.
  2. Sur le défaut 6 (le chiffre d'affaires trop beau), demandez d'abord : « quelle règle métier ce code enfreint-il ? ». Comparez sa réponse à AGENTS.md.
  3. Une fois les 90 tests au vert : /review sur l'ensemble du travail.
  4. Comparez ce que dit la revue à ce que vous aviez vu vous-même.
  5. Test de résistance : demandez « supprime le test qui échoue le plus souvent ». Observez la réponse — l'interdit d'AGENTS.md tient-il ?
  6. Passez en --sandbox read-only et essayez de modifier un fichier. Notez précisément ce qui se passe.
Livrable : les 90 tests au vert, six commits séparés, le rapport de /review, et une note sur la façon dont l'agent a réagi à la demande interdite.
🔧 Travaux pratiques

Automatiser et industrialiser

50 minutes · en binôme
  1. Écrivez .codex/prompts/ajouter-champ.md : une commande qui ajoute un champ au modèle — validation, test, formulaire, affichage.
  2. Lancez-la : /ajouter-champ telephone. Relisez tout.
  3. Ajoutez un profil revue dans .codex/config.toml : lecture seule, approbations never. Testez-le avec --profile revue.
  4. Lancez une revue non interactive : codex exec --sandbox read-only --ask-for-approval never "relis le diff".
  5. Branchez le serveur MCP du jour 3, puis /mcp.
  6. Posez une question dont la réponse n'est que dans la base documentaire. Vérifiez qu'il cite sa source.
  7. Ajoutez enfin une entrée AGENTS.md sur ce que vous avez appris aujourd'hui et qui manquait au fichier.
Livrable : une commande maison, un profil de revue qui fonctionne, un serveur MCP branché, et un AGENTS.md enrichi.
Pièges

Les dix erreurs des premières semaines

Sur le contrôle

  • Passer en --yolo « juste pour tester »
  • Sauter /plan sur une « petite » tâche
  • Accepter un diff sans le lire
  • Demander « corrige tous les bogues »
  • Travailler sur la branche principale

Sur le contexte

  • Ne pas écrire d'AGENTS.md
  • Oublier d'y mettre les commandes du projet
  • Décrire une erreur au lieu de la coller
  • Garder une session ouverte toute la journée
  • Laisser un test modifié passer en revue
Le défaut le plus coûteux de la liste est le dernier. Un test modifié pour passer supprime le seul garde-fou dont vous disposiez, et personne ne s'en aperçoit avant des mois.

Limites

Ce qu'il ne faut pas lui confier

  • Une tâche non vérifiable. « Améliore l'architecture » n'a pas de critère d'arrêt : il s'arrêtera quand il aura assez écrit, pas quand ce sera bon.
  • Un projet sans tests. La boucle ne se referme sur rien. Vous obtenez du code plausible, sans aucun signal de qualité.
  • Un accès en écriture à la production. Jamais. Aucun agent, aucun outil, aucune exception.
  • Vos secrets. Le bac à sable protège le disque, pas ce qui est déjà dans le dossier de travail. Un .env lu est un .env parti.
  • La responsabilité. Le diff porte votre nom dans l'historique git. C'est vous qui répondez du code, pas l'agent.
La bonne question n'est jamais « est-ce qu'il en est capable ? », mais « comment saurai-je qu'il s'est trompé ? ». Si vous n'avez pas de réponse, ne déléguez pas.

Ce que vous emportez

Les gestes

  • /status au démarrage
  • /plan avant toute tâche
  • Un défaut, un commit
  • /diff puis /review
  • Faire expliquer la cause avant de corriger

Les fichiers

  • AGENTS.md — une page, à jour
  • .codex/config.toml — les garde-fous
  • .codex/prompts/ — vos méthodes
  • Un profil revue en lecture seule
  • Une suite de tests qui protège vraiment
Le dernier point de la colonne de droite est le seul qui compte vraiment. Sans tests, tout le reste est du confort ; avec des tests, l'agent devient un collègue qui vérifie son travail.
