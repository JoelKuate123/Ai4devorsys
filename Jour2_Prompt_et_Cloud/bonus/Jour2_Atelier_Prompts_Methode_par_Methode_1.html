Formation « IA pour les développeurs » · Jour 2 · Module 3 en pratique

Un site par prompts, méthode par méthode

Un client vous envoie un e-mail. Vous allez construire son site dans GitHub Copilot sans écrire une ligne de code vous-même. À chaque étape, une méthode du cours : on vous explique comment elle fonctionne, on vous donne un prompt qui marche à copier-coller, puis vous l'améliorez. Le site est terminé et en ligne à la dernière étape.

La demande

De : marc.dubois@… · Objet : site internet du club · mardi 9 septembre

Je suis le président du Club Sportif de la Basilique, une ASBL de quartier à Koekelberg (Avenue de la Basilique 385, 1081) qui existe depuis 1987. On a trois salles, un terrain extérieur et une équipe de bénévoles. Je voudrais créer un site pour ça : les gens du quartier nous cherchent sur leur téléphone et ne trouvent rien.

Il faudrait une présentation du club, la liste des activités, un tableau des horaires, quelques témoignages de membres et un formulaire de contact. Nos activités : Basket (mardi et jeudi 18h-20h, dès 8 ans), Yoga (samedi 9h-10h, adultes, sur inscription), Football (mercredi 17h-19h, dès 6 ans), Boxe (lundi et vendredi 19h-21h, dès 14 ans), Gym douce (mardi 10h-11h, seniors), Escalade (sur réservation, dès 10 ans), Volley (jeudi 20h-22h, adultes), Danse (mercredi 14h-15h30, 6-12 ans). L'accueil est ouvert du lundi au vendredi de 17h à 20h.

Nos couleurs sont le vert forêt (#1F6F4A) et le sable (#F2E9D8). Pas de réseaux sociaux ni d'icônes partout, on veut quelque chose de simple. Personne chez nous ne saura maintenir du code compliqué, donc le plus simple possible. Notre slogan : « Le sport pour tous, à Koekelberg, depuis 1987 ».

Tout ce que vous savez du projet est dans cet e-mail. Ce qui n'y est pas est « à déterminer » : un bon prompt ne laisse pas le modèle l'inventer.

Le prompt détaillé : les six blocs

Résultat : le squelette du site — index.html et style.css

Comment ça fonctionne

Le modèle ne connaît ni votre projet ni vos contraintes : face à une demande floue, il choisit l'interprétation la plus banale. Un prompt professionnel se lit comme un ticket pour un développeur qu'on n'a jamais rencontré. Il a six parties :

RÔLEqui parle, avec quelle expertise
CONTEXTEle projet, ce qui existe, les contraintes
TÂCHEune seule action, un verbe précis
CONTRAINTESce qui est imposé ou interdit
FORMATla forme exacte de la réponse
EXEMPLEun morceau du résultat attendu

Prompt à copier-coller (mode Edit)

RÔLE
Tu es intégrateur web, spécialisé en HTML sémantique et CSS sans dépendance.

CONTEXTE
Site du Club Sportif de la Basilique, ASBL de quartier à Koekelberg, consulté surtout sur téléphone. Personne au club ne maintiendra du JavaScript.

TÂCHE
Crée la structure vide du site.

CONTRAINTES
- Deux fichiers seulement : index.html et style.css.
- lang="fr", meta charset et viewport, un seul h1 avec le nom du club.
- Un nav avec une liste de liens vers #presentation, #activites, #horaires, #temoignages, #contact.
- Cinq sections avec cet id et un h2, vides sinon. Un footer vide.
- Aucun JavaScript, aucune police ni bibliothèque externe.
- Sous 600 px, les liens du menu passent à la ligne. Focus clavier visible.

FORMAT
Crée les deux fichiers, puis liste en cinq lignes ce que contient chacun.

EXEMPLE d'un lien du menu :
<li><a href="#activites">Activités</a></li>
Vous devez voirdeux fichiers, une page avec le titre et six liens, cinq sections vides. Rien d'autre : pas de contenu inventé, pas de README, pas de script.

À vous : comment améliorer ce prompt ?

  1. Relancez-le sans le bloc CONTEXTE. Qu'est-ce qui change dans le menu ?
  2. Le CSS produit contient-il des couleurs ou une grille que vous n'avez pas demandées ? Quelle contrainte l'empêcherait ?
  3. Réécrivez le prompt avec votre amélioration, relancez, gardez la meilleure version.
git add -A && git commit -m "1 squelette"

Le rôle : donner un métier au modèle

Résultat : la section Présentation, accessible

Comment ça fonctionne

« Tu es un architecte logiciel senior » déplace la zone de probabilité : vocabulaire, niveau de détail, préoccupations. Un rôle efficace a trois parties :

Un métier précis« intégrateur spécialisé en accessibilité » bat « expert mondial »
Ce qu'il vérifietrois contrôles concrets — c'est ça qui oriente vraiment la réponse
Comment il répond« concis, sans préambule ni flatterie » évite le « En tant qu'expert… »

Prompt à copier-coller (mode Edit)

Tu es un intégrateur web, spécialisé en accessibilité.
Tu vérifies systématiquement :
- que chaque image a un alt qui décrit ce qu'elle montre
- que le texte de chaque lien dit où il mène
- qu'il n'y a qu'un seul h1 par page
Tu réponds de façon concise et technique, sans préambule ni flatterie.

Dans #file:index.html, remplis la section #presentation avec :
- le slogan « Le sport pour tous, à Koekelberg, depuis 1987 » ;
- un paragraphe à partir de ces faits : ASBL depuis 1987, trois salles, un terrain extérieur, une équipe de bénévoles ;
- l'image images/salle.jpg ;
- un lien vers #contact pour s'inscrire.
Ne modifie rien en dehors de cette section. Termine par la liste des lignes ajoutées.
Vous devez voirun slogan en paragraphe (pas un deuxième h1), un alt descriptif, un lien dont le texte dit où il mène, et aucune autre section touchée.

À vous : comment améliorer ce prompt ?

  1. Remplacez les trois contrôles par « Tu es un expert mondial du web » et relancez dans une nouvelle conversation. Comparez le alt et le lien.
  2. Quel quatrième contrôle ajouteriez-vous au rôle pour cette section ? (indice : la hiérarchie des titres)
git add -A && git commit -m "2 presentation"

Le few-shot : montrer plutôt qu'expliquer

Résultat : huit cartes d'activités identiques dans leur structure

Comment ça fonctionne

Deux exemples bien choisis remplacent un paragraphe de consignes : le modèle copie la forme avant le fond. Trois règles :

Exemples dans le format exactdu HTML réel, pas une description du HTML
Un cas limite parmi euxc'est là que le modèle dérape sinon
La dernière ligne en suspens« Sortie : » sans rien après — le modèle complète le motif

Prompt à copier-coller (mode Ask, puis collez le résultat dans la section #activites)

Transforme chaque activité en une carte HTML, en respectant strictement la structure des exemples.

Exemple 1 —
Entrée : Basket (mardi et jeudi 18h-20h, dès 8 ans)
Sortie :
<article class="carte">
  <h3>Basket</h3>
  <p class="horaire">Mardi et jeudi, 18 h – 20 h</p>
  <p class="public">Dès 8 ans</p>
</article>

Exemple 2 —
Entrée : Yoga (samedi 9h-10h, adultes, sur inscription)
Sortie :
<article class="carte">
  <h3>Yoga</h3>
  <p class="horaire">Samedi, 9 h – 10 h</p>
  <p class="public">Adultes — sur inscription</p>
</article>

Entrée : Football (mercredi 17h-19h, dès 6 ans)
Entrée : Boxe (lundi et vendredi 19h-21h, dès 14 ans)
Entrée : Gym douce (mardi 10h-11h, seniors)
Entrée : Escalade (sur réservation, dès 10 ans)
Entrée : Volley (jeudi 20h-22h, adultes)
Entrée : Danse (mercredi 14h-15h30, 6-12 ans)
Sortie :
Vous devez voirsix cartes de plus, mêmes balises, mêmes classes ; Escalade sans horaire inventé ; Danse « 14 h – 15 h 30 ».

À vous : comment améliorer ce prompt ?

  1. Remplacez l'exemple Yoga par une activité « simple » (Football). Relancez : qu'arrive-t-il à Escalade ?
  2. Complétez la ligne « Sortie : » vous-même avec la première carte. Le résultat est-il encore complet ?
  3. Comment transformer ce prompt pour que Copilot insère directement les cartes dans le fichier (mode Edit) sans toucher au reste ?
git add -A && git commit -m "3 activites"

Le chain-of-thought : raisonner avant de coder

Résultat : les cartes en grille responsive

Comment ça fonctionne

Demander de raisonner par étapes : chaque étape écrite devient le contexte de la suivante, et le modèle se trompe moins. Utile pour un choix ou un diagnostic, inutile pour une transformation mécanique. Trois parties :

Le problèmeen deux ou trois phrases, sans hypothèse
L'ordre imposéreformuler, lister, comparer, conclure
Une conclusion limitéetrois lignes maximum, sinon l'utile est noyé

Prompt à copier-coller (mode Ask)

Dans #file:index.html, la section #activites contient huit article.carte. Je veux quatre colonnes sur grand écran et une seule sous 600 px, sans JavaScript.

Procède dans cet ordre :
1. Reformule le besoin en une phrase.
2. Liste ce que tu sais du contexte et ce qui te manque.
3. Propose deux techniques CSS différentes.
4. Compare-les : simplicité, robustesse à 400 px, lisibilité pour un débutant.
5. Conclus par une seule recommandation, sans la coder.

Termine par une section « CONCLUSION » de trois lignes maximum.

Puis, en mode Edit : « Implémente la CONCLUSION dans #file:style.css, sans modifier index.html ni aucune règle existante. Liste les règles ajoutées. »

Vous devez voirdeux techniques réellement comparées, une conclusion courte, puis une grille 4 → 1 colonnes et un diff vide sur index.html.

À vous : comment améliorer ce prompt ?

  1. Retirez « sans la coder » et relancez. Où finit le raisonnement ? Pourquoi est-ce un problème ?
  2. Le raisonnement affiché vous a-t-il convaincu ? Vérifiez la conclusion dans le CSS : le raisonnement n'est pas une preuve.
  3. Ajoutez une étape 3 bis : « pour chaque technique, ce qui casse si une carte a un titre très long ».
git add -A && git commit -m "4 grille"

Le format de sortie : du texte au JSON, du JSON au tableau

Résultat : la section Horaires

Comment ça fonctionne

Un texte libre est fait pour un humain, du JSON est fait pour du code. Le format se montre par un exemple de structure, jamais par une description. Trois parties :

La structure montréeun objet exemple avec les clés exactes
La règle du manquant« null », jamais une invention
Rien autour« aucun texte avant ni après » — sinon le code ne peut pas lire

Prompt à copier-coller (mode Ask)

Extrais tous les créneaux d'activité de #file:index.html.
Réponds UNIQUEMENT par un tableau JSON de cette forme exacte, un objet par créneau :
[
  {"activite": "Basket", "jour": "mardi", "debut": "18:00", "fin": "20:00", "public": "dès 8 ans"}
]
Une activité sur plusieurs jours donne plusieurs objets. Heures au format HH:MM.
Si une information est absente, écris null. N'invente jamais de valeur.
Aucun texte avant. Aucun texte après.

Relisez le JSON (Basket : deux objets ; Escalade : null ; Danse : 15:30). Puis, en mode Edit : « Voici les créneaux validés : [JSON]. Remplis la section #horaires de #file:index.html avec un tableau trié par jour puis par heure, avec caption et th scope="col". Les activités sans créneau vont dans une phrase sous le tableau. Ne modifie rien d'autre. »

Vous devez voirdu JSON pur, dix objets dont Escalade à null ; puis un tableau de neuf lignes, trié, et une phrase pour l'escalade.

À vous : comment améliorer ce prompt ?

  1. Retirez « Aucun texte avant. Aucun texte après. ». Que se passe-t-il ? Où faut-il aussi répéter cette ligne ?
  2. Décrivez le format en prose (« un JSON avec l'activité, le jour… ») au lieu de le montrer. Relancez deux fois : les clés sont-elles les mêmes ?
  3. Quelle contrainte manque pour que « mardi et jeudi » ne soit jamais un seul objet ?
git add -A && git commit -m "5 horaires"

L'itération : une contrainte à la fois

Résultat : la section Témoignages

Comment ça fonctionne

Aucun prompt n'est bon du premier coup. On écrit court, on lance, on regarde ce qui cloche, on ajoute une seule contrainte, on relance. Une modification à la fois, sinon on ne sait pas laquelle a produit l'amélioration. Trois parties :

Version courtedeux lignes, on lance
Un défaut, une contrainteon corrige le prompt, pas le résultat
Un journalversion, contrainte ajoutée, effet — comme un historique Git

Prompt v1 à copier-coller (mode Edit)

Dans #file:index.html, remplis la section #temoignages avec trois témoignages de membres du club.
Vous devez voirquelque chose qui cloche : témoignages trop longs, noms complets inventés, pas de balise sémantique, rien n'indique qu'ils sont fictifs. C'est voulu.

À vous : améliorez ce prompt en trois tours

  1. Notez UN défaut. Ajoutez UNE contrainte qui le corrige. git checkout -- ., relancez.
  2. Répétez jusqu'à v4. Contraintes attendues quelque part dans votre journal : prénom seul et deux phrases ; blockquote et cite ; commentaire HTML « témoignages provisoires, à remplacer avec accord écrit ».
  3. Relancez v4 deux fois : la structure est-elle identique ? Si oui, le prompt est stable.
git add -A && git commit -m "6 temoignages v4"

La modification cadrée : changer une chose, et rien d'autre

Résultat : les couleurs du club, en variables CSS

Comment ça fonctionne

L'erreur du débutant : « améliore cette page ». Le modèle réécrit tout, renomme, supprime, et vous ne savez plus ce qui a bougé. La bonne méthode a trois parties :

Le fichier existantfourni tel quel
MODIFICATION DEMANDÉE / NE MODIFIE PASune phrase, puis une liste explicite
La liste des lignes changéesdemandée à la fin : votre diff à relire en trois secondes

Prompt à copier-coller (mode Edit)

Voici le fichier existant : #file:style.css

MODIFICATION DEMANDÉE :
Applique les couleurs du club — vert forêt #1F6F4A et sable #F2E9D8 — en les déclarant une seule fois dans :root et en les réutilisant partout ; tout texte garde un contraste d'au moins 4,5:1 avec son fond.

NE MODIFIE PAS :
- les noms de classes et de sélecteurs
- les largeurs, marges, grilles et points de rupture
- l'ordre des règles
- les tailles de police

Applique les changements, puis liste les lignes réellement changées avec leur numéro.
Vous devez voirdes variables dans :root, plus aucune couleur en dur, et une liste de lignes qui correspond exactement à git diff style.css.

À vous : comment améliorer ce prompt ?

  1. Dans une autre conversation : « améliore les couleurs de #file:style.css ». Regardez le diff. Annulez. Combien de choses ont changé sans qu'on le demande ?
  2. La liste annoncée par Copilot correspond-elle au diff réel ? Si non, quelle ligne du NE MODIFIE PAS manquait ?
  3. Réutilisez ce même gabarit pour le pied de page (méthode 8) : c'est le prompt que vous écrirez le plus souvent dans votre métier.
git add -A && git commit -m "7 couleurs"

Négation, clarté, position : dire ce qu'on veut

Résultat : le pied de page

Comment ça fonctionne

« Ne mets pas d'emoji » marche mal ; « écris uniquement en texte brut » marche. Trois réglages :

Interdit + alternativechaque « ne … pas » est accompagné de ce qu'on veut à la place
Un verbe par phrase« analyse, résume et propose » sera mal exécuté
Début et finla contrainte critique est placée en première et en dernière ligne

Prompt à copier-coller (mode Edit)

Le pied de page contient uniquement du texte et un seul lien.

Remplis le footer de #file:index.html avec, sur quatre lignes :
1. Club Sportif de la Basilique — Avenue de la Basilique 385, 1081 Koekelberg
2. Accueil : du lundi au vendredi, de 17 h à 20 h
3. ASBL — numéro d'entreprise : à déterminer
4. un lien « Retour en haut » vers le header (ajoute-lui id="haut").
Style dans #file:style.css : fond sable, texte vert forêt, avec les variables de :root, 14 px minimum.

Le pied de page contient uniquement du texte et un seul lien. Aucune icône, aucune image, aucun réseau social.
Vous devez voirun footer de quatre lignes, un seul lien, aucun pictogramme, et « à déterminer » resté tel quel.

À vous : comment améliorer ce prompt ?

  1. Relancez avec la version de Marc : « Fais un pied de page. Pas d'icônes, pas de réseaux sociaux, pas trop long. » Comptez les icônes.
  2. Supprimez la répétition de la première ligne en fin de prompt. Le résultat change-t-il ?
  3. Reformulez « pas trop long » en contrainte chiffrée.
git add -A && git commit -m "8 pied de page"

La chaîne de prompts : découper pour réussir

Résultat : le formulaire de contact, validé sans JavaScript

Comment ça fonctionne

Un prompt qui demande cinq choses en réussit trois. La solution : une chaîne, où chaque maillon est testable et relu avant le suivant. Un prompt qui fait cinq choses est un mauvais prompt, comme une fonction qui fait cinq choses.

Maillon 1 : déciderla liste des champs, en tableau, relue par vous
Maillon 2 : produirele HTML à partir du tableau validé
Maillon 3 : finirle CSS des états

Maillon 1 à copier-coller (mode Ask)

Besoin : formulaire de contact d'un club de sport. Le visiteur donne son nom, son e-mail, l'activité qui l'intéresse (parmi les huit de #file:index.html), un message, et accepte que ses données servent uniquement à lui répondre.

Réponds uniquement par un tableau : Champ | Élément et type HTML | Obligatoire | Attributs de validation natifs | Texte d'aide (une phrase).
Aucun code, aucun texte avant ni après le tableau.

Relisez et corrigez le tableau (Copilot ajoute souvent un téléphone que personne n'a demandé). Puis maillon 2, mode Edit : « Voici les champs validés : [tableau]. Remplis la section #contact de #file:index.html avec ce formulaire : chaque champ avec un label relié par for/id, ses attributs de validation, un small d'aide ; un bouton “Envoyer la demande” ; aucun JavaScript. Ne modifie rien d'autre. » Puis maillon 3 : « Dans #file:style.css, ajoute le style du formulaire : champs pleine largeur (560 px max), label en gras au-dessus, bordure rouge sombre sur :user-invalid, bouton vert forêt. Variables de :root uniquement. Ne touche à aucune règle existante. »

Vous devez voircliquer un libellé donne le focus au champ ; l'envoi vide et un e-mail sans @ sont refusés par le navigateur ; le select contient exactement les huit activités.

À vous : comment améliorer cette chaîne ?

  1. Demandez tout en un seul prompt dans une autre conversation. Comptez ce qui manque (consentement ? labels ? select complet ?).
  2. Quel maillon pourrait être confié à un modèle moins cher ? Lequel ne peut pas ?
  3. Ajoutez un maillon 4 : « liste les cas limites du formulaire auxquels je n'ai pas pensé ».
git add -A && git commit -m "9 formulaire"

La self-consistency : voter plutôt que croire

Résultat : le site vérifié, puis publié

Comment ça fonctionne

On pose la même question fermée N fois, dans N conversations séparées, et on garde la réponse majoritaire. Le modèle se trompe de façon aléatoire : il se trompe rarement trois fois de la même manière. Si les trois divergent, c'est le signal le plus utile : la question passe à un humain.

Une question ferméeréponse en un mot, sans justification
Trois conversations séparéespas trois messages à la suite : le modèle se répète
Le vote, puis la vérificationon ouvre la ligne annoncée dans le fichier

Question à poser trois fois (trois nouvelles conversations, mode Ask)

Dans #file:style.css, existe-t-il une règle qui provoque un débordement horizontal sur un écran de 400 px de large ?
Réponds par « oui » suivi du numéro de ligne, ou par « non ». Sans justification.
Vous devez voirtrois réponses notées, une majorité, et la ligne vérifiée dans le fichier. Testez aussi vous-même à 400 px (F12, mode appareil).

À vous : et pour finir, publiez

  1. Notez les trois réponses. Si elles divergent, que faites-vous ?
  2. Écrivez, avec les six blocs de la méthode 1, le prompt qui demande la procédure de publication sur GitHub Pages (dépôt public, branche main, dossier racine), commandes incluses. Relisez chaque commande avant de l'exécuter.
  3. Envoyez l'URL à Marc. Objectif atteint.
git add -A && git commit -m "10 publication" && git push

Ce que vous emportez

  • Un site en ligne, construit sans écrire de code, en dix prompts que vous pouvez relire, expliquer et refaire.
  • Dix versions améliorées de votre main : c'est votre bibliothèque de départ. Exportez-les.
  • Une habitude : quand le résultat est mauvais, on corrige le prompt, jamais le code.
