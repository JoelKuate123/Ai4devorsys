Les LLM

Architecture, réglages, formats, et la mécanique du RAG

Architecture

Ce qu'il y a dans un LLM

  • Un tokeniseur : découpe le texte en tokens et les convertit en numéros.
  • Une table d'embeddings : chaque numéro de token devient un vecteur de nombres.
  • N couches de transformer, empilées : chacune contient un bloc d'attention et un petit réseau de neurones.
  • Une couche de sortie : produit un score pour chacun des dizaines de milliers de tokens possibles.
  • Un échantillonneur : choisit le token suivant parmi les mieux notés. C'est là qu'agissent température et top_p.
Le nombre de paramètres (7B, 70B, 400B) compte les nombres stockés dans ces couches. Plus il y en a, plus le modèle capte de nuances — et plus il consomme de mémoire et d'électricité.

Réglages

La température : le seul bouton que vous tournerez vraiment

  • À chaque étape, le modèle a une liste de tokens candidats avec leur probabilité.
  • La température déforme cette liste : basse, elle accentue les écarts ; haute, elle les aplatit.
  • Température 0 : le modèle prend toujours le token le plus probable. Résultat quasi reproductible.
  • Température 1 : distribution d'origine. Réponses variées, plus créatives.
  • Température > 1,5 : le modèle part dans des directions improbables. En pratique, inexploitable.
Même à température 0, la reproductibilité n'est pas garantie : l'ordre des calculs sur GPU et les mises à jour du modèle côté fournisseur peuvent changer le résultat. Ne construisez jamais une logique métier sur l'hypothèse d'une sortie identique.

Fonctionnalités

Les trois tâches où un LLM est irremplaçable

Summarization

Résumer un texte long. Précisez toujours la longueur cible et l'angle : « en cinq puces, pour un directeur financier ». Sans angle, le résumé est plat.

Classification

Ranger un texte dans des catégories. Donnez la liste fermée des catégories, une définition de chacune, et un exemple. Sortie en JSON.

Extraction

Sortir des champs structurés d'un texte libre : dates, montants, noms, références. C'est l'usage le plus rentable en entreprise.

Ces trois tâches ont un point commun : l'entrée est du texte que vous possédez. Le modèle ne fabrique pas d'information, il la réorganise. C'est là qu'il est le plus fiable et le moins cher.

Extraction

Extraire des données d'un texte libre : le cas type

  • Entrée : un e-mail, un compte rendu, un PDF de facture, une réclamation.
  • Sortie voulue : un objet JSON avec des champs typés, prêt à insérer en base.
  • Trois règles qui font la différence : liste fermée des champs, null si absent, jamais d'invention.
  • Ajoutez un champ confiance : il vous permet de router vers un humain les cas douteux.
  • Et un champ citation : le passage exact du texte d'où vient l'information. C'est votre traçabilité.
Le champ citation est un excellent réflexe : si le modèle ne peut pas citer le passage, c'est presque toujours qu'il a inventé la valeur.

Obtenir un dictionnaire Python, pas du texte

commun/llm_client.py
def demander_json(prompt, systeme=None, temperature=0.2):
    """Comme demander(), mais renvoie un dictionnaire Python."""

    texte = demander(prompt, systeme=systeme,
                     temperature=temperature, format_json=True)

    # Les modèles ajoutent souvent ``` autour du JSON. On les enlève.
    texte = texte.strip()
    if texte.startswith("```"):
        lignes = texte.split("\n")
        texte = "\n".join(lignes[1:-1])   # on retire 1re et dernière ligne

    try:
        return json.loads(texte)
    except json.JSONDecodeError:
        # On renvoie une erreur exploitable plutôt que de planter
        return {"erreur": "réponse non parsable", "texte_brut": texte}
Le bloc try / except final n'est pas de la paranoïa : un modèle produit du JSON invalide plusieurs fois sur mille. À l'échelle d'un service, cela arrive tous les jours.

Formats

Étude du fichier GGUF

  • Un fichier GGUF contient deux choses : les tenseurs (les poids) et les métadonnées.
  • Les métadonnées comprennent : l'architecture, le tokeniseur complet, le gabarit de conversation, la longueur de contexte.
  • C'est ce qui le rend autonome : un seul fichier suffit pour faire tourner le modèle. Pas de dépendances éparpillées.
  • Le gabarit de conversation est essentiel : il dit comment écrire les rôles system, user et assistant pour ce modèle précis.
  • Créé pour llama.cpp, il est aujourd'hui lu par LM Studio, Ollama, GPT4All, et des bibliothèques Python.

Local

Pourquoi installer un LLM sur sa machine

  • Confidentialité totale : aucune donnée ne quitte le poste. C'est souvent le seul argument qui compte.
  • Coût nul au token : vous pouvez traiter un million de documents sans regarder la facture.
  • Fonctionnement hors ligne : utile en déplacement, sur un site isolé, ou derrière un réseau fermé.
  • Reproductibilité : le modèle ne change pas sous vos pieds. Votre test d'il y a six mois vaut encore.
  • Apprentissage : voir le modèle charger, occuper la mémoire et ralentir démystifie complètement la technologie.
Ce que vous perdez : de la qualité brute, et de la vitesse sur un poste sans carte graphique. Pour classer, extraire ou faire du RAG documentaire, c'est très souvent suffisant.

Embeddings

Les modèles d'embedding : petits, rapides, économiques

  • Un modèle d'embedding ne génère pas de texte : il transforme un texte en vecteur. C'est tout.
  • Il est bien plus petit qu'un LLM : quelques dizaines à quelques centaines de millions de paramètres.
  • Il tourne sans difficulté sur un processeur ordinaire — et le coût en API est très inférieur à la génération.
  • Critère de choix numéro un pour nous : le multilingue. Un modèle entraîné sur l'anglais rapproche mal deux phrases françaises.
  • Règle absolue : le même modèle doit servir à indexer et à interroger. Deux modèles différents produisent des vecteurs incomparables.
Conséquence pratique lourde : changer de modèle d'embedding oblige à réindexer toute la base. Choisissez-le avec soin dès le départ.

DIMENSION = 128   # les vrais modèles : 384, 768, 1536 ou 3072

def embedding(texte, dimension=DIMENSION):
    """1. découper en mots utiles  2. chaque mot vote pour une case
       3. normaliser (longueur ramenée à 1)"""

    vecteur = [0.0] * dimension          # on part de zéros

    mots = decouper_en_mots(texte)       # minuscules, sans accents, sans mots vides

    for mot in mots:
        # Le "hashing trick" : le même mot tombe toujours dans la même case
        position = _position_du_mot(mot, dimension)
        vecteur[position] += 1.0

    return normaliser(vecteur)


def normaliser(vecteur):
    """Sans cette étape, un texte long aurait des scores plus élevés."""
    longueur = math.sqrt(sum(v * v for v in vecteur))

    if longueur == 0:
        return vecteur

    return [v / longueur for v in vecteur]

La similarité cosinus : dix lignes de géométrie

exercice_5_embeddings/embeddings_maison.py
def similarite_cosinus(vecteur_a, vecteur_b):
    """1 = même sens · 0 = aucun rapport · -1 = opposés"""

    if len(vecteur_a) != len(vecteur_b):
        raise ValueError("Tailles différentes : comparaison impossible")

    norme_a = math.sqrt(sum(v * v for v in vecteur_a))
    norme_b = math.sqrt(sum(v * v for v in vecteur_b))

    if norme_a == 0 or norme_b == 0:
        return 0.0          # un vecteur nul n'a pas de direction

    # zip(a, b) parcourt les deux listes en parallèle
    produit = sum(x * y for x, y in zip(vecteur_a, vecteur_b))

    return produit / (norme_a * norme_b)

#   « congé parental »  vs  « demande de congé parental »   -> 0.447

La réduction de dimension : voir ce qu'on ne peut pas voir

  • Un embedding a 128, 768 ou 1 536 dimensions. Personne ne peut se représenter cela.
  • La réduction de dimension projette ces vecteurs sur 2 ou 3 axes, pour les dessiner.
  • On perd de l'information, forcément. Mais on gagne quelque chose de précieux : on voit les groupes.
  • Méthodes courantes : PCA (rapide, linéaire), t-SNE et UMAP (meilleurs groupes visuels, plus lents).
  • Usage professionnel réel : repérer les doublons, les documents mal classés, ou les zones où votre base est vide.
Un nuage de points d'embeddings est souvent le meilleur outil de diagnostic d'un RAG qui répond mal : si tous vos documents forment un seul amas, aucune recherche ne pourra les distinguer.

Code · exercice 5

Une base vectorielle en trente lignes

exercice_5_embeddings/embeddings_maison.py
class BaseVectorielle:
    """Chroma, Qdrant et pgvector ajoutent la persistance et les index.
    Le principe de la recherche est exactement celui-ci."""

    def __init__(self, dimension=DIMENSION):
        self.dimension = dimension
        self.documents = []

    def ajouter(self, texte, metadonnees=None):
        self.documents.append({
            "texte": texte,
            "vecteur": embedding(texte, self.dimension),
            "metadonnees": metadonnees or {},   # source, page, droits...
        })

    def rechercher(self, question, nombre_de_resultats=3):
        # 1. la question devient un vecteur, avec LE MÊME embedding
        vecteur_question = embedding(question, self.dimension)

        resultats = []

        # 2. on compare la question à CHAQUE document
        for document in self.documents:
            score = similarite_cosinus(vecteur_question, document["vecteur"])
            resultats.append({"texte": document["texte"],
                              "score": round(score, 4),
                              "metadonnees": document["metadonnees"]})

        # 3. on trie du plus proche au plus lointain, 4. on garde les N premiers
        resultats.sort(key=lambda ligne: ligne["score"], reverse=True)
        return resultats[:nombre_de_resultats]

Débrief exercice 5

Ce que cet exercice démontre

  • Un embedding n'a rien de magique : des mots, des cases, une addition, une division.
  • La normalisation n'est pas un détail : sans elle, les longs documents gagneraient toujours.
  • Une base vectorielle, à petite échelle, c'est une liste et une boucle. Le produit sert quand le volume grandit.
  • Les métadonnées ne sont pas optionnelles : sans elles, pas de citation, pas de filtre par droits, pas de confiance.
  • Le choix de la dimension est un compromis précision contre poids, que vous mesurez maintenant vous-même.

transformers et datasets : exécuter un modèle depuis Python

LangChain : à quoi ça sert vraiment

  • LangChain fournit des briques standardisées : chargeurs de documents, découpeurs, embeddings, bases vectorielles, chaînes.

Bonnes pratiques

Dix règles d'usage des outils d'IA en développement

  • 1. Un seul endroit dans le code appelle le modèle. Un seul.
  • 2. Le prompt vit dans une fonction, versionnée dans Git.
  • 3. La sortie du modèle est validée par du code avant tout usage.
  • 4. Les tests ne font jamais d'appel réel : on utilise des doublures.
  • 5. Un chemin dégradé existe pour le cas où le modèle est indisponible.
  • 6. Les clés sont dans l'environnement, jamais dans le code ni dans les journaux.
  • 7. Le coût est estimé avant le développement, et mesuré après.
  • 8. On choisit le plus petit modèle qui réussit la tâche.
  • 9. Chaque réponse destinée à un utilisateur cite sa source ou est validée par un humain.
  • 10. On mesure la qualité sur un jeu de cas réels, pas sur une impression.

Évaluation

Mesurer la qualité : le sujet dont personne ne parle

  • Constituez un jeu de vingt à cinquante cas réels, avec la réponse attendue. C'est votre référence.
  • Rejouez-le à chaque changement : de prompt, de modèle, de découpage, de version.
  • Mesurez séparément la recherche (le bon extrait est-il remonté ?) et la rédaction (la réponse est-elle fidèle ?).
  • Suivez le taux de « je ne sais pas » : trop bas, votre système invente ; trop haut, il est inutile.
  • Journalisez les questions sans réponse : c'est la meilleure liste de documents à ajouter à votre base.
Sans jeu d'évaluation, vous ne saurez jamais si votre modification a amélioré ou dégradé le système. Vous naviguerez à l'impression — et l'impression, en IA, est particulièrement trompeuse.

RAG · recherche

Recherche hybride et reclassement : les deux améliorations qui paient

  • Le problème : la recherche vectorielle comprend le sens, mais rate les termes exacts — une référence, un code produit, un numéro d'article.
  • La recherche hybride combine deux scores : le vectoriel (le sens) et le lexical, type BM25 (les mots exacts).
  • Le gain est souvent spectaculaire sur des documents techniques bourrés de références.
  • Le reclassement (reranking) : on récupère vingt candidats, puis un petit modèle spécialisé les réordonne finement, et on n'en garde que trois.
  • Coût : un modèle de plus dans la chaîne, et quelques centaines de millisecondes.
Ordre d'intervention conseillé quand un RAG répond mal : 1. le découpage · 2. la recherche hybride · 3. le reclassement · 4. seulement ensuite, un plus gros modèle. C'est l'ordre du meilleur rapport gain / effort.

Au-delà du texte

L'appel d'outils : quand le modèle décide d'exécuter votre code

  • Vous déclarez à l'API une liste de fonctions disponibles, avec leur description et leurs paramètres.
  • Le modèle ne les exécute pas : il demande à ce qu'on les exécute, en renvoyant un nom de fonction et des arguments en JSON.
  • C'est votre code qui exécute, puis renvoie le résultat au modèle, qui rédige alors la réponse finale.
  • C'est ainsi qu'on règle les limites du jour 1 : une vraie calculatrice, une vraie requête en base, une vraie recherche web.
  • La description de chaque fonction est un prompt : sa qualité détermine si le modèle appelle la bonne fonction.
Règle de sécurité absolue : vous décidez de ce que vous exécutez. Ne branchez jamais directement une sortie de modèle sur une commande système, une suppression en base ou un virement. Validez les arguments comme une entrée utilisateur hostile.

Au-delà du texte

Les agents : une boucle, pas une intelligence

  • Un agent est une boucle : le modèle réfléchit, choisit un outil, votre code l'exécute, le résultat revient, et on recommence.
  • La boucle s'arrête quand le modèle estime la tâche terminée — ou quand vous avez atteint la limite d'itérations que vous avez fixée.
  • Cette limite n'est pas optionnelle : sans elle, une boucle peut tourner des heures et coûter très cher.
  • Les agents brillent sur les tâches vérifiables : le code, où les tests disent si c'est bon.
  • Ils échouent sur les tâches dont personne ne sait dire objectivement si le résultat est correct.
Question à se poser avant tout projet d'agent : « comment saurai-je automatiquement que le travail est bien fait ? » Sans réponse à cette question, il ne faut pas construire un agent.

MCP : brancher un assistant sur vos systèmes

Model Context Protocol. Une norme ouverte pour qu'un assistant appelle vos outils, au lieu que vous copiiez-colliez vos données dans un chat.

  • Le serveur — le vôtre — expose des outils : chercher un document, lire une base, appeler une API interne.
  • Le client — Claude Code, Codex, Copilot CLI, l'application Claude — les découvre et les appelle.
  • Le transport le plus courant : l'entrée et la sortie standard d'un processus. Une ligne de JSON par message.
  • Le protocole sous-jacent : JSON-RPC 2.0. Trois méthodes suffisent à faire un serveur utile.
  • Écrit une fois, votre serveur fonctionne avec tous les assistants compatibles. C'est tout l'intérêt d'une norme.
Ce que cela change concrètement : votre base documentaire de l'exercice 6 devient interrogeable par un assistant, sans qu'aucun document ne quitte votre machine. L'assistant reçoit l'extrait utile, pas le fichier.

Sécurité

Faire tourner un modèle local n'est pas sans risque

  • Un modèle téléchargé est un fichier venu d'internet. Vérifiez l'éditeur : compte officiel, nombre de téléchargements, licence lisible.
  • Préférez les formats sûrs. Les anciens formats basés sur la sérialisation Python pouvaient exécuter du code au chargement. GGUF et safetensors sont conçus pour éviter cela.
  • Un modèle peut avoir été volontairement altéré pour produire certaines réponses dans certains contextes. C'est indétectable à l'œil.
  • Le serveur local écoute sur un port : vérifiez qu'il n'est pas exposé au réseau de l'entreprise sans authentification.
  • Journalisez quel modèle exact, et quelle version, a produit quelle réponse. En cas de contrôle, c'est ce qu'on vous demandera.
Un serveur LM Studio lancé sur 0.0.0.0 au lieu de 127.0.0.1, c'est un modèle accessible à tout le réseau local, sans mot de passe. Vérifiez ce réglage.

Découper : la fonction qui décide de tout

exercice_6_rag_local/rag.py
def decouper(texte, taille=600, chevauchement=100):
    """Le chevauchement évite de couper une phrase importante en deux."""

    if len(texte) <= taille:
        return [texte.strip()] if texte.strip() else []

    morceaux = []
    debut = 0

    while debut < len(texte):
        fin = debut + taille
        morceau = texte[debut:fin]

        # On préfère couper à la fin d'une phrase plutôt qu'au milieu d'un mot
        if fin < len(texte):
            position_point = morceau.rfind(". ")

            # Seulement si le point est dans la seconde moitié,
            # sinon les morceaux deviendraient bien trop courts
            if position_point > taille // 2:
                morceau = morceau[:position_point + 1]
                fin = debut + position_point + 1

        if morceau.strip():
            morceaux.append(morceau.strip())

        # max(..., debut + 1) garantit qu'on avance : anti-boucle-infinie
        debut = max(fin - chevauchement, debut + 1)

    return morceaux

def indexer(dossier=None):
    """PHASE 1 du RAG : une fois, à l'avance. En production : chaque nuit."""

    dossier = Path(dossier) if dossier else DOSSIER_DOCUMENTS
    base = BaseVectorielle()

    if not dossier.exists():
        print(f"[rag] Dossier introuvable : {dossier}")
        return base            # base vide plutôt qu'un plantage

    # sorted() : ordre stable d'une exécution à l'autre
    for fichier in sorted(dossier.glob("*.txt")):

        contenu = fichier.read_text(encoding="utf-8")
        morceaux = decouper(contenu)

        for numero, morceau in enumerate(morceaux):
            base.ajouter(morceau, metadonnees={
                "source": fichier.name,   # SANS ÇA : pas de citation possible
                "morceau": numero,        # position dans le document
            })

    return base

def repondre(question, base, nombre_dextraits=3, seuil=0.05):

    # --- R comme Retrieval : la recherche (exercice 5) ---
    resultats = base.rechercher(question, nombre_de_resultats=nombre_dextraits)

    # --- On écarte les extraits trop peu pertinents ---
    extraits = [l for l in resultats if l["score"] >= seuil]

    # --- Rien de pertinent : on N'APPELLE PAS le modèle du tout ---
    #     On économise un appel ET on évite une réponse inventée.
    if not extraits:
        return {"reponse": "Je ne trouve pas cette information dans les documents fournis.",
                "sources": [], "extraits": [], "modele_appele": False}

    # --- A comme Augmented : on enrichit le prompt (exercice 3) ---
    prompt = construire_prompt(question, extraits)

    # --- G comme Generation : le modèle rédige (exercice 2) ---
    #     temperature 0.1 : fidélité aux documents, pas de créativité
    reponse = demander(prompt, systeme=INSTRUCTION_SYSTEME, temperature=0.1)

    # --- On remonte les sources, sans doublon, pour que l'humain vérifie ---
    sources = []
    for extrait in extraits:
        source = extrait["metadonnees"].get("source")
        if source and source not in sources:
            sources.append(source)

    return {"reponse": reponse, "sources": sources,
            "extraits": extraits, "modele_appele": True}

MCP : le protocole qui relie tout

Cinq messages JSON, et votre base documentaire devient un outil que n'importe quel assistant sait appeler.

MCP · le protocole

Tout le protocole tient en cinq messages

  • initialize — la poignée de main : version du protocole, capacités, nom du serveur.
  • notifications/initialized — le client confirme. Aucun « id » : on ne répond pas.
  • tools/list — le catalogue. Le modèle ne verra que ce que vous décrivez ici.
  • tools/call — l'exécution, avec les arguments choisis par le modèle.
  • La réponse — toujours une liste de blocs de contenu : c'est ce qui permet de renvoyer du texte, une image ou un document avec la même structure.

def traiter_message(message):
    methode = message.get("method")
    identifiant = message.get("id")
    parametres = message.get("params") or {}

    if methode == "initialize":
        return reponse_ok(identifiant, {
            "protocolVersion": "2024-11-05",
            "capabilities": {"tools": {}},        # on n'expose que des outils
            "serverInfo": {"name": "rag-documentaire-local", "version": "1.0.0"}
        })

    # Une notification n'a pas d'« id » : y répondre CASSE le client.
    if methode == "notifications/initialized":
        return None

    if methode == "tools/list":
        return reponse_ok(identifiant, {"tools": OUTILS})

    if methode == "tools/call":
        nom = parametres.get("name")
        arguments = parametres.get("arguments") or {}

        if nom not in IMPLEMENTATIONS:
            return reponse_erreur(identifiant, -32602, f"Outil inconnu : {nom}")

        try:
            texte = IMPLEMENTATIONS[nom](arguments)
            return reponse_ok(identifiant, {
                "content": [{"type": "text", "text": texte}], "isError": False})

        except Exception as erreur:
            # On ne laisse JAMAIS une exception remonter : elle tuerait le
            # serveur. On renvoie l'erreur comme un RÉSULTAT : le modèle
            # peut alors la lire et changer de stratégie.
            return reponse_ok(identifiant, {
                "content": [{"type": "text", "text": f"L'outil a échoué : {erreur}"}],
                "isError": True})

def boucle_principale():
    """Lit l'entrée standard ligne par ligne, répond sur la sortie standard."""
    for ligne in sys.stdin:
        ligne = ligne.strip()
        if not ligne:
            continue

        try:
            message = json.loads(ligne)
        except json.JSONDecodeError:
            ecrire(reponse_erreur(None, -32700, "JSON illisible"))
            continue

        reponse = traiter_message(message)
        if reponse is not None:          # None = notification : on se tait
            ecrire(reponse)


def ecrire(objet):
    sys.stdout.write(json.dumps(objet, ensure_ascii=False) + "\n")
    # flush() force l'envoi IMMÉDIAT. Sans lui, Python garde le texte en
    # mémoire tampon et le client attend une réponse qui ne vient jamais.
    sys.stdout.flush()


def journal(message):
    # La sortie standard est RÉSERVÉE au protocole. Un seul print() de
    # débogage casse la communication, sans message d'erreur.
    sys.stderr.write(f"[serveur-mcp] {message}\n")
Les deux erreurs qui coûtent le plus cher : un print() oublié dans le serveur, et un flush() manquant. Dans les deux cas : aucun message d'erreur, juste un silence.

Trois questions avant d'exposer un outil

  • Que se passe-t-il si le modèle l'appelle au mauvais moment ? Un outil lire_document est sans danger. Un outil supprimer_client ne devrait pas exister sans confirmation humaine.
  • Que voit le modèle en retour ? Tout ce que l'outil renvoie entre dans le contexte, y compris ce que vous n'aviez pas prévu d'y mettre — une colonne « commentaire interne », par exemple.
  • Qui peut appeler ce serveur ? En transport stdio, c'est l'utilisateur de la machine. Sur un transport réseau, c'est une autre affaire : authentification obligatoire.
Règle simple pour commencer : des outils en lecture seule. On ouvre l'écriture plus tard, outil par outil, avec un test à chaque fois.
